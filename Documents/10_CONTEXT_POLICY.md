# 10. コンテキスト運用方針

> **この文書は毎セッション読み込まれない。**必要になったときだけ読む。
> 常時強制される規則は `CLAUDE.md` §10 にある。ここにはその根拠と手順を置く。
>
> 最終更新: 2026-08-20 / 出典確認日: 2026-08-20

---

## 0. なぜこれが必要か

会話が長くなるとトークンを大量に消費する。理由は2つで、どちらも避けられない。

1. **リクエストごとに会話全体が再送される。**プロンプトキャッシュにより単価は下がるが、
   量そのものは減らない。何時間も開いたままのセッションで一行質問しても、
   会話全体分の使用量が発生する [4]
2. **コンテキストが埋まるほど精度が落ちる。**モデルは以前の指示を「忘れ」、
   誤りが増える [2]

つまりこれは**コスト問題であると同時に品質問題**である。GPU 時間と同じく、
コンテキストは有限の予算として管理する。

セッション開始時点で既に約 7,700 トークンが自動的に読み込まれている
(システムプロンプト 4,200 / プロジェクト CLAUDE.md 1,800 / スキル記述 450 /
ユーザ CLAUDE.md 320 ほか)。ソースファイル1本の読み込みが 1,100–2,400 トークン [3]。
**本研究の `runs/*/log.txt` や `predictions/` は桁が2つ違う。**

## 1. 採用する3つの中核技術

Anthropic が公開しているエージェント向けコンテキスト設計の指針は、
中核を3つに整理している [1]。本プロジェクトへの対応は以下。

| 技術 | 内容 | 本プロジェクトでの実装 |
|---|---|---|
| **構造化された外部メモ** | 会話ではなくファイルを記憶装置にする | **既に `STATE.md` / `CHANGELOG.md` / `DECISIONS.md` がこれ。**`AGENTS.md` の大原則「情報伝達は必ずファイル経由」と同一 |
| **サブエージェント** | 独立したコンテキストで探索させ、要約(典型的に 1,000–2,000 トークン)だけ返す | 文献の原典確認、arXiv 月次監視、コード探索を委譲 |
| **圧縮(compaction)** | 会話履歴を要約して再開する。決定と未解決事項を残し、冗長なツール出力を捨てる | `/compact` + `CLAUDE.md` の Compact instructions |

**この repo は既に外部メモの規約を持っている。**だから `/clear` を安全に使える
── これが本プロジェクト最大の利点である。`STATE.md` を読めば作業を再開できる
設計になっている以上、会話履歴を抱え込む理由がない。

さらに **just-in-time retrieval**(必要になった時点で識別子から取りに行く)[1] を
ファイル読み込みの原則とする。§3。

## 2. セッションの切り方

### 2.1 原則: 1セッション = 1 PLAN

`plans/PLAN-XXX-*.md` 1本が1セッション。終わったら `STATE.md` を更新して `/clear`。

```
セッション開始 → CLAUDE.md §1 の起動手順 → PLAN 実行 → STATE.md 更新 → /clear
```

`/clear` はコストがゼロである。一方 `/compact` は要約対象の会話を読み直すため、
**巨大なコンテキストでの `/compact` はそれ自体が大きなリクエストになる** [4]。

| 状況 | 使うもの |
|---|---|
| PLAN が終わった / 無関係な作業に移る | **`/clear`**(先に `STATE.md` を更新) |
| 同じ作業の途中だが会話が長い | `/compact` に指示を付ける |
| 後で戻る可能性がある | `/rename` してから `/clear`、後で `/resume` |
| 文脈に残す必要のない小さな確認 | `/btw`(答えが会話履歴に入らない) |

### 2.2 撤退基準

**同じ問題で2回訂正しても直らなければ、3回目を同じセッションで続けない。**
コンテキストが失敗した試行で汚染されている。`/clear` して、
学んだことを含めた具体的なプロンプトで再開する方が速い [2]。

これは本プロジェクトでは特に重要で、パーサの取りこぼしや評価スクリプトのバグは
「惜しい失敗」を大量に生む。それが全部コンテキストに残ると、
以降の判断が過去の失敗案に引きずられる。

### 2.3 長時間放置しない

プロンプトキャッシュの有効期間はサブスクリプションで1時間、
API キーや使用クレジット利用時は5分 [4]。それを超えて再開すると
全コンテキストが再処理される。**中断するなら `/clear` してから離れる。**

### 2.4 長くなったら、エージェントの側から切る

セッションを切る判断をユーザーに任せない。**気づいた側が止める。**
エージェントは以下のどれかに当てはまった時点で作業を中断し、skill `handoff` を実行する
(ADR-015)。

| 徴候 | 判定方法 |
|---|---|
| コンテキストが約 100k トークンを超えた | hook `context-guard` が実測して警告する |
| コンテキストが約 140k トークンを超えた | 同上。**ここでは新しい作業を始めない** |
| PLAN を1本終えた | §2.1 |
| 話題が PLAN の範囲外に移った | §2.1 |
| 同じ問題で2回訂正しても直らない | §2.2 撤退基準 |
| 大きな出力を3回以上コンテキストに流した | §3.2 |

#### 実測の方法 — `infra/context_guard.py`

`UserPromptSubmit` hook として `.claude/settings.json` に登録してある。
transcript の JSONL から**直近のアシスタント応答が実際に消費した入力トークン数**
(`input_tokens + cache_creation_input_tokens + cache_read_input_tokens`)を読む。
推測ではなく実測である(`CLAUDE.md` §7)。

- 閾値未満なら**何も出力しない**。警告そのものがトークンを食わないようにしてある
- 100k の警告はセッションにつき1回だけ。140k の警告は毎プロンプト出る
- 閾値は環境変数 `CONTEXT_GUARD_WARN` / `CONTEXT_GUARD_URGENT` で上書きできる
- hook が動かない環境でも規約は生きる。**上の表は人間とエージェントの側の義務である**

#### 引き継ぎの成果物

| ファイル | 役割 |
|---|---|
| `STATE.md` の「引き継ぎ」 | 恒久的な状態。次セッションが §1 の開始手順で読む |
| `logs/HANDOFF.md` | **次セッションに貼るプロンプトそのもの。**毎回上書き(履歴は git) |

手順は skill `handoff`。**会話にしか無い情報がゼロになってから `/clear` する。**

## 3. ファイル読み込みの規律 ★この repo で最も効く

本研究が生成する成果物は巨大である。全文を読む理由はほぼない。

### 3.1 読んではいけないもの

| 対象 | 代わりに |
|---|---|
| `runs/*/log.txt` | `tail -n 50` / `grep -n "ERROR\|Traceback"` |
| `runs/*/predictions/` | `jq` で必要なキーだけ。件数は `wc -l` |
| `runs/*/metrics.json`(多数) | `jq -s '[.[] \| {seed, rule_rate}]'` で集約してから |
| `data/` の生成済みデータセット | `head -20` + `wc -l`。中身の確認はテストで行う |
| 設計文書の全文 | `grep -n` で節を特定し `sed -n 'X,Yp'` |
| `refs.bib` 全体 | `grep -A8 "@article{key"` |

### 3.2 大きな出力はファイルに落としてから要約する

```bash
python -m code.eval.run --run-dir runs/... > /tmp/eval.log 2>&1
tail -30 /tmp/eval.log
grep -c "parse_fail" /tmp/eval.log
```

標準出力を直接コンテキストに流し込まない。

### 3.3 テスト出力のフィルタ

`pytest` の全出力ではなく失敗だけを見る。

```bash
pytest code/tests -q 2>&1 | tail -20
```

恒久的にやるなら PreToolUse フックで自動フィルタできる(数万トークンを
数百トークンに落とせる)[4]。Phase 0 でテストが増えたら導入を検討する。

### 3.4 探索は範囲を切る

「〜を調査して」と無限定に投げると、大量のファイルが読まれてコンテキストが埋まる [2]。
範囲(ディレクトリ・ファイル名・観点)を明示するか、subagent に委譲する。

## 4. サブエージェントへの委譲

独立したコンテキストで動き、要約だけを返す [1][2]。**探索コストを本会話から隔離できる。**

### 4.1 委譲すべき作業

| 作業 | 理由 |
|---|---|
| **文献の原典確認**(`02_RELATED_WORK.md` §F、`CLAUDE.md` §3) | 大量のページを開く。結論は「著者・年・会議・URL」だけ |
| **arXiv 月次監視**(`06_THREATS.md` T11) | 大量の abstract を読む。返すのは該当の有無と数件 |
| コードベースの横断探索 | 多数ファイルを読む |
| 冗長なコマンド出力の処理 | 生ログは subagent 側に留まる [4] |
| 実装後の敵対的レビュー(CRITIC 的作業) | 新鮮なコンテキストの方が良いレビューになる [2] |

### 4.2 委譲の規約

1. **結論だけ返させる。**生ログ・全文引用を返させない
2. **結果は必ずファイルに書かせる。**会話に返っただけの情報は次のセッションで消える
   (`AGENTS.md` の大原則)
3. **範囲と完了条件を明示する。**曖昧な委譲は subagent 側でコンテキストを溢れさせる
4. モデルは作業に見合ったものを指定する(単純な探索は Sonnet / Haiku)

### 4.3 注意: エージェントチームは高い

複数の Claude インスタンスを並列で走らせる agent teams は、
plan モードで**通常セッションの約7倍**のトークンを使う [4]。
各インスタンスが独自のコンテキストを持つため。**本プロジェクトでは使わない。**
`AGENTS.md` の役割分担は「同時並列」ではなく「順次の受け渡し」として運用する。

## 5. 圧縮(compact)の運用

`/compact` に指示を付けると、何を残すかを制御できる [2][4]。

```
/compact PLAN-003 の run_id と4値の実測、および予測とのずれに集中して要約せよ
```

恒久的な指示は `CLAUDE.md` の Compact instructions セクションに置いてある。
研究記録として致命的なのは、**要約の過程で run_id が数値から切り離されること**である
(`CLAUDE.md` §2「実験結果でない数値を文書に書く」の禁止に直接抵触する)。
そのため「run_id のない数値は残さず捨てる」を明示的に指示している。

## 6. 常時読み込まれるものを削る

### 6.1 CLAUDE.md

毎セッション全文が読み込まれる。公式の目安は **200行以下** [4]。
Phase 固有の手順・長い説明・たまにしか使わない知識は、
必要になったときだけ読む文書に置く。

判断基準 [2]:
> この行を消したら Claude が間違えるか? 間違えないなら消す。

肥大した CLAUDE.md は「読まれるが従われない」状態を作る。
**規則を足すほど各規則の遵守率が下がる**というトレードオフを忘れない。

**本 repo の履歴**: §10 の追加で 263 行に膨れたため、ADR-011 で
実験実行手順を `infra/RUNPOD.md` §4 へ、コード規約を skill `code-style` へ移した(198 行)。
残したのは「どのセッションでも破ってはいけない規則」だけである。

### 6.1.1 skill に逃がす

skill(`.claude/skills/<名前>/SKILL.md`)は **description だけが常時読み込まれ、
本文は呼び出されたときに読まれる** [5]。したがって「特定の役割のセッションでしか
使わない長い手順」の置き場所として CLAUDE.md より安い。

| 常時読み込む(CLAUDE.md) | 呼ばれたときだけ読む |
|---|---|
| 破ると研究が壊れる禁止事項、記録の義務、承認が要る判断 | 実装のスタイル規約(skill `code-style`) |
| どの役割のセッションでも適用される手順 | 役割固有の運用手順(`infra/RUNPOD.md`) |

**description は常時コストなので短く書く。**本文に何が書いてあるかではなく、
「いつ読むべきか」を書く。skill 一覧の文字数予算はコンテキスト窓の約1%で、
溢れると使用頻度の低い skill から description が削られる [5]。
実際の占有量は `/context` の Skills 行で確認できる(§8)。

### 6.2 MCP サーバ

MCP のツール定義は既定で遅延読み込みされ、名前だけがコンテキストに入る [4]。
それでも使わないサーバは無効にする。**RunPod MCP は RUNNER セッションでのみ有効にする。**
PLANNER / IMPLEMENTER / ANALYST のセッションでは不要。

CLI で済むものは CLI を使う(`gh` など)。CLI はツール一覧のコストがゼロ [2][4]。

## 7. モデルと思考予算の選択

| 作業 | モデル |
|---|---|
| 設計判断、統計計画、結果の解釈、事前登録の文言 | Opus |
| 実装、パーサ、集計スクリプト、データ生成、定型リファクタ | Sonnet |
| subagent の単純探索 | Sonnet / Haiku |

思考(extended thinking)は出力トークンとして課金される [4]。
定型実装では `/effort` を下げる。**ただし `CLAUDE.md` §8 に挙げた
「エージェントに任せてはいけないこと」の周辺では下げない。**

## 8. 測定する

推測しない。`CLAUDE.md` §7 の批判的視点はここにも適用される。

| コマンド | 見るもの |
|---|---|
| `/context` | いま何がコンテキストを占めているか |
| `/usage` | セッションのトークン内訳、プラン使用量、10%以上を占める挙動の警告 |
| `/insights` | 直近セッションの作業パターンと摩擦点の HTML レポート |

ステータスラインにコンテキスト使用率を常時表示させると、
埋まってから気づく事故がなくなる [2]。

## 9. チェックリスト(セッション終了時)

`CLAUDE.md` §9 に加えて:

```
[ ] 結論はファイルに書いたか(会話にしか無い情報が残っていないか)
[ ] STATE.md の引き継ぎセクションは、これだけ読めば再開できる内容か
[ ] 次のセッションは /clear から始められる状態か
[ ] 一時ファイル(/tmp の大きなログ)は消したか、あるいは runs/ に正しく置いたか
```
