## ADR-001: 主軸を「除去型病変」から「変換型病変」に変更する

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 当初は能力を劣化させる病変を主軸としていたが、波及を観測しても「表現共有」と「非特異的劣化」を区別できず、間接的な議論しかできない。
- 決定: 規則的変換(+2 など)を主軸とし、除去型は対照条件に位置づけ直す。
- 根拠: 変換は固有の指紋を持つため、指紋の一致は劣化の相関では説明できない。
- 帰結: 主指標が「性能低下量」から「規則一致率(rule_rate)」へ。4値分解が必須になる。

## ADR-003: 主ドメインを算術とし、色は将来の展開とする

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 色・数の両方が候補だった。
- 決定: 算術を主ドメインとする。色は `08_FUTURE_DIRECTIONS.md` に記載し、直近では扱わない。
- 根拠:
  1. 色の補色病変は FT もテストも色語を出力するため、「出力語彙のリマップ」で転移が説明できてしまう
  2. 算術は複合問題・単位元・比較判断など、文字列操作では説明できない診断が豊富
  3. 数は amodal 概念の代表格で、理論的射程が広い
  4. Feucht et al. (2026) という明確な接続点がある
- 帰結: 色ドメインの評価系は後回し。ただし評価ハーネスはドメイン非依存に設計し、後から色を足せるようにする。

## ADR-004: 主変換を ×2 から +2 に変更する ★重要

- 日付: 2026-08-20
- ステータス: 採択(~~**ADR-007 の旧案を置き換える**~~ → **本 ADR はどの ADR も置き換えない。**
  2026-08-21、ADR-014 により誤記として取り消し。ADR-007(同等性検定)は現状のまま有効。
  **本 ADR の決定内容そのものは無効化されない**)
- 文脈: 以前は「×2 は末尾桁の編集で達成できないため表層ショートカット耐性が高い」として ×2 を推していた。
- 決定: **+2 を主変換とする。×2 は非結合的な変換の対照条件としてのみ使う。**
- 根拠: 代数的な事実による。
  - a⊕b = a+b+2 は可換かつ**結合的**で、φ(x)=x+2 により (Z,+) と同型。単位元 −2、逆元 −a−4。**整合した代替算術が well-defined に存在する**
  - a⊗b = 2(a+b) は結合的でない。(a⊗b)⊗c = 4a+4b+2c ≠ a⊗(b⊗c) = 2a+4b+4c
  - ゆえに **×2 では「モデルは整合した別世界に移行したか」という主問い自体が立てられない**
- 帰結:
  - G2(代数的整合性)の全項目が +2 に依存して設計される
  - ×2 の表層耐性という利点は失われる。代わりに G2・G6 が文字列操作では説明できないことを防御とする(`06_THREATS.md` T3)
  - `code/tests/test_algebra.py` でこの代数的事実を形式検証し、設計の前提を固定する
- 代替案: ×2+1 のようなアフィン変換(出力段階と演算ごとで分岐し、かつ実計算を要する)。学習コストが上がるため主変換にはしないが、補助条件として検討の余地あり。

## ADR-006: 反復単位を項目ではなく FT run とする ★重要

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 「1つの FT モデルに1000項目を解かせて n=1000」とする論文が散見されるが、これは誤り。FT の効果を主張するなら、1つの FT モデルは1つの実現値である。
- 決定: **条件効果の検定はシード間分散に対して行う。主要評価項目は1条件あたり10シード、副次的評価項目は5シード。**
- 根拠: 条件は被験モデル間要因であり、項目数を増やしても条件効果の検出力はほとんど上がらない。増やすべきはシードである。
- 帰結:
  - 交差ランダム効果モデル `(1|seed) + (1|item) + (1|template)` を使う
  - シード別集計の単純解析も併記し、混合効果モデルと一致するかを確認
  - GPU コストが増える。Phase 1 でグリッドを絞ることが必須になる
  - 検出力分析をシミュレーションベースで実験前に行う

- 帰結: `05_STATISTICS.md` §5。Phase 0 でプロンプト感受性を測る必要が生じる(境界の根拠になるため)。

## ADR-010: コンテキスト運用を明文化し、1セッション=1 PLAN を原則とする

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 会話が長くなるとトークン消費が増える。リクエストごとに会話全体が再送されるため、長時間開いたセッションでは一行の質問でも会話全体分の使用量が発生する。同時に、コンテキストが埋まるほどモデルの遵守精度が落ち、過去の指示を取りこぼす。**コスト問題であると同時に品質問題である。**
- 決定: コンテキストを GPU 時間と同様の有限予算として管理する。中核は3つ。(1) 1セッション = 1 PLAN とし、終了時に `STATE.md` を更新して `/clear` する。(2) 探索の重い作業(文献の原典確認、arXiv 監視、横断探索)を SCOUT サブエージェントに委譲し、結論のみを返させる。(3) `runs/` の生成物と巨大なコマンド出力を全文読まず、`grep` / `tail` / `jq` で必要部分だけ取る。強制規則を `CLAUDE.md` §12 に、根拠と手順を `10_CONTEXT_POLICY.md` に置く。
- 根拠: Anthropic のエージェント向けコンテキスト設計指針が挙げる3技術(外部メモ・サブエージェント・圧縮)のうち、**外部メモは本 repo が既に持っている**(`STATE.md` / `CHANGELOG.md` / `DECISIONS.md`、および `AGENTS.md` の「情報伝達は必ずファイル経由」)。したがって `/clear` を安全に使えるという他プロジェクトにない利点があり、最も安価な手段(`/clear` はコストゼロ、`/compact` は要約対象を読み直すため高い)を主戦略にできる。出典は `10_CONTEXT_POLICY.md` §出典。
- 帰結:
  - `CLAUDE.md` に §12 と Compact instructions を追加。**同ファイルが 263 行になり、公式の目安 200 行を超過した。**次の見直しで §6(実験実行手順)と §7(コード規約)の別ファイル化を検討する
  - `AGENTS.md` に SCOUT 役割と依頼雛形を追加
  - 圧縮時に「run_id から切り離された数値は捨てる」を明示。§2 の禁止事項(実験結果でない数値を文書に書く)が要約経由で破られるのを防ぐため
  - agent teams は使わない(通常の約7倍のトークンを消費する)
  - RunPod MCP は RUNNER セッションでのみ有効にする
- 代替案:
  - **`/compact` を主戦略にする**: 却下。区切りが明確な作業では `/clear` の方が安く、かつ要約による情報損失がない。本 repo は `STATE.md` があるため `/clear` の損失がほぼゼロ
  - **CLAUDE.md に何も足さず運用で対処する**: 却下。`AGENTS.md` の大原則と同じ理由で、規約に書かれていないことは守られない
  - **Phase 固有の手順まで CLAUDE.md に書く**: 却下。常時読み込みのコストが上がり、規則の遵守率が下がる

## ADR-011: CLAUDE.md を強制規則のみに絞り、手順と規約を外部化する

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: ADR-010 で §12 と Compact instructions を追加した結果 `CLAUDE.md` が 263 行になり、公式の目安 200 行を超過した。同 ADR に「次の見直しで §6/§7 の別ファイル化を検討する」と負債として記録してあった。CLAUDE.md は毎セッション全文が読み込まれるため、超過は常時コストであると同時に、**規則を足すほど各規則の遵守率が下がる**という品質問題でもある。ADR-010 の変更自体がそのトレードオフに乗っていた。
- 決定: `CLAUDE.md` には「どの役割のセッションでも破ってはいけない規則」だけを残し、役割固有の手順は外に出す。

  - §7 コード規約 → skill `.claude/skills/code-style/SKILL.md`(IMPLEMENTER セッションでしか使わない)
  - §12.3(CLAUDE.md 自体の運用)→ §10.2 の1行に圧縮。根拠と判断基準は `10_CONTEXT_POLICY.md` §6.1
  - 残った節を繰り上げて番号を詰める
- 根拠: skill は **description だけが常時コンテキストに載り、本文は呼び出されたときに読まれる**(`10_CONTEXT_POLICY.md` §6.1.1、出典 [5])。役割固有の手順を skill と `infra/` に逃がせば、常時コストを払わずに規約そのものは保持できる。ADR-010 が却下した「規約に書かず運用で対処する」ではなく、「書く場所を変える」で解く。
- 帰結:
  - `CLAUDE.md` 263 → 198 行。目安 200 行以下を回復し、**ADR-010 の既知の負債は解消**
  - `CLAUDE.md` の節番号(旧→新): 8→6、9→7、10→8、11→9、12→10、12.1→10.1、12.2→10.2、12.3→削除。§0–§5 は不変。**ADR-010 以前の文書に現れる §番号は旧番号である**
  - `infra/RUNPOD.md` の節番号(旧→新): 4→5、5→6、6→7、7→8、8→9。§1–§3 は不変
  - 参照を更新: `AGENTS.md`(IMPLEMENTER 依頼雛形)、`04_EXPERIMENT_PLAN.md`、`07_ROADMAP.md`、`10_CONTEXT_POLICY.md`、`README.md`

- 代替案:
  - **欠番(§6/§7 を空ける)のままにする**: 却下。既存の参照は保てるが、以後「なぜ欠番か」を毎セッション説明することになる。番号対応表をこの ADR に残す方が安い
  - **コード規約を `infra/` の通常文書に置く**: 却下。skill なら description が常時載るため、IMPLEMENTER が「規約の存在自体に気づかない」事故を防げる。通常文書は参照されなければ存在しないのと同じ
  - **§6 を `04_EXPERIMENT_PLAN.md` に置く**: 却下。同ファイルは「何を測るか」の設計文書であり、実行手順を混ぜると事前登録の対象範囲が曖昧になる

## ADR-013: `code/` を維持し、標準ライブラリ `code` を再エクスポートして共存させる

- 日付: 2026-08-20
- ステータス: 採択(人間が3案から選択)
- 文脈: `README.md` の構造図どおりに `code/__init__.py` を作成した時点で、
  `pytest code/tests -q` が**テストの実行前に**落ちるようになった。

  ```
  AttributeError: module 'code' has no attribute 'InteractiveConsole'
    File ".../pdb.py", line 316, in <module>
      class _PdbInteractiveConsole(code.InteractiveConsole):
  ```

  pytest は起動時に `pdb` を import し、`pdb` は標準ライブラリ `code` の
  `InteractiveConsole` を継承する。repo ルートが `sys.path` の先頭にあるため
  `import code` が本 repo のパッケージに解決され、標準ライブラリが隠れていた。
  `CLAUDE.md` §4 が全変更の前提としている pytest ゲートが機能しない状態だった。
- 決定: **ディレクトリ名 `code/` を維持し、`code/__init__.py` で標準ライブラリ
  `code.py` の公開名(`InteractiveInterpreter` / `InteractiveConsole` /
  `interact` / `compile_command`)を再エクスポートする。**

## ADR-014: ADR-004 はどの ADR も置き換えない。「ADR-007 の旧案」は誤記として取り消す

- 日付: 2026-08-21
- ステータス: **採択**(2026-08-21、人間が「AI 判断をもって対処」と指示。
  `STATE.md` の承認待ち項目 1 に対応)

## ADR-015: セッションを切る判断をエージェントの義務にし、実測 hook と引き継ぎ skill で支える

- 日付: 2026-08-21
- ステータス: **採択**(2026-08-21、人間の指示。「長くなったと判断したら次のエージェント向けの
  プロンプトを作り、ユーザーに伝えてセッションを変えさせたい」)
- 文脈: 対話型セッションは、長くなるほど毎リクエストで会話全体が再送され、精度も落ちる
  (`Documents/10_CONTEXT_POLICY.md` §0)。既存の規約は「1セッション = 1 PLAN」「終わったら
  `/clear`」を定めていたが、**切る判断の主体が誰かを決めていなかった。**結果として、
  区切りが曖昧なまま会話が伸び続ける。`STATE.md` の引き継ぎ形式は `AGENTS.md` にあるが、
  「次のセッションにそのまま貼れるプロンプト」という成果物は定義されていなかった。
- 決定: 3点セットで導入する。
  1. **義務化**: `CLAUDE.md` §10.2 に「長くなったら自分から止める」を追加。判定基準は
     `Documents/10_CONTEXT_POLICY.md` §2.4 の表(トークン量 / PLAN 完了 / 話題変更 /
     撤退基準 / 大出力の反復)
  2. **実測**: `infra/context_guard.py` を `UserPromptSubmit` hook として登録
     (`.claude/settings.json`)。transcript の JSONL から直近の
     `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` を読み、
     100k で1回、140k で毎回警告する。閾値未満は**何も出力しない**
  3. **引き継ぎ**: skill `handoff`。`STATE.md` を更新し、`logs/HANDOFF.md` に
     次セッション用プロンプトを上書きし、ユーザーに `/clear` を促すまでを1手順にする
- 根拠:
  - **推測ではなく実測できる。**transcript の各アシスタント応答は `usage` を持つ。
    キャッシュ読み出しを含めた入力トークン合計が、そのリクエストで実際に送られた
    コンテキストの大きさである。`CLAUDE.md` §7「推測しない」に沿う
  - **警告自体のコストをゼロにできる。**閾値未満は標準出力に1バイトも書かない
  - **`/clear` はコストがゼロ。**切る判断を早めに倒しても損をしない(§2.1)
- 代替案と却下理由:
  - **エージェントの自己判断だけにする**: 基準を明文化しても、長い会話ほど見落とす。
    見落としが起きる場面こそ発動してほしいので、機械的な検知を併用する
  - **hook だけにする**: 警告は出るが引き継ぎの中身が担保されない。
    `logs/HANDOFF.md` の型がないと、次セッションが会話履歴を必要とする状態が残る
  - **`/compact` に寄せる**: 要約対象の会話を読み直すため高い。加えて要約の過程で
    run_id が数値から切り離される危険がある(`CLAUDE.md` §2 の禁止に直接抵触)
- 未検証・リスク:
  - **hook が実際に発火するかは未確認。**`UserPromptSubmit` は次のプロンプト送信時に走るため、
    導入したセッション内では検証できない。`.claude/settings.json` は本セッション開始時点で
    存在しなかったので、**Claude Code の再起動が必要な可能性がある**
  - hook のペイロードに `transcript_path` が無い版に備え、`session_id` と `cwd` から
    `~/.claude/projects/<sanitized-cwd>/<session_id>.jsonl` を再構成するフォールバックを持つ。
    どちらでも解決できなければ**黙って何もしない**(プロンプトを妨げない)
  - **閾値 100k / 140k は運用値であり、実験的根拠はない。**本 repo の既存セッションの
    実測(最大 165k)から、余裕をもって引き継げる水準として置いた。環境変数で上書きできる
  - 出力は `ensure_ascii=True` に固定した。Windows の stdout の既定エンコーディングが
    UTF-8 とは限らず、日本語をそのまま流すと受け側に壊れたバイト列が渡りうるため
- 関連 ADR: 011(`CLAUDE.md` を強制規則のみに絞り、手順を skill へ外部化する)

## ADR-016: `rule_rate` を「条件自身の規則」ではなく「固定した参照規則」に対して定義する ★重要

- 日付: 2026-08-22
- ステータス: **採択**(2026-08-22、人間が `plans/PLAN-001-eval-battery.md` §12 の承認待ち-1 を承認)
- 文脈:
  - `CLAUDE.md` §6 は4値分解(`correct_rate` / `rule_rate` / `other_error_rate` /
    `parse_fail_rate`、合計 1.0)を全病変対象タスクに義務づけているが、`rule_rate` の
    「**病変規則**」が**どの条件の規則を指すのか**を決めていなかった。
    素直に読めば「その run の条件が持つ規則」である
  - `Documents/05_STATISTICS.md` §2 は主要評価項目を
    「G6 の `rule_rate` を `p2` と `ident` の間で比較」と定める
  - `code/lesion.py:140` の `IdentityLesion` の docstring は
    「定義上あらゆる項目で真値と規則適用値が一致するため、この条件の `rule_rate` は解釈できない」
    と書く。実際 `IdentityLesion.coincides` は常に `True` を返す(`code/lesion.py:143`)
  - **この2つは両立しない。**「条件自身の規則」で計算すると `ident` では規則値 = 真値なので
    `rule_rate(ident) = correct_rate(ident)` となる。`p2` との差は「病変が入ったか」ではなく
    「素の算術能力がどれだけ落ちたか」を測ってしまい、**主要評価項目が literal には成立しない**
- 決定: 5点を定める。
  1. **`rule_rate` は固定した参照規則 `r` に対して定義する。**表記は `rule_rate@r`。
     「応答が、参照規則 `r` を真値に適用した値と一致した率」である
  2. **`eval.reference_rule` を `configs/template.yaml` の必須項目にする。**
     `null` で置き、**既定値を作らない**(skill `code-style` §1, §5)
  3. **主要評価項目では参照規則を `p2`(offset=2、ADR-004 の主変換)に固定する。**
     全条件(`p2` / `arb` / `x2` / `ident` / `none`)で**同一の参照規則**に対する4値分解を計算する
  4. **`metrics.json` は参照規則ごとに独立した4値ブロックを持つ。**
     **合計 1.0 は各ブロックの内部で成立する。**ブロックをまたいだ合計に意味はない

     ```json
     {
       "primary_reference_rule": "p2",
       "by_reference_rule": {
         "p2": {"correct_rate": null, "rule_rate": null,
                "other_error_rate": null, "parse_fail_rate": null},
         "x2": {"correct_rate": null, "rule_rate": null,
                "other_error_rate": null, "parse_fail_rate": null}
       }
     }
     ```

     `correct_rate` と `parse_fail_rate` は参照規則に依存しないが、
     **各ブロック内で合計 1.0 を成立させるためブロックごとに再掲する。**
     `other_error_rate` は参照規則に依存する(ある参照規則で `rule` に入る応答が、
     別の参照規則では `other_error` に落ちる)
  5. 条件自身のペネトランスを見たい場合(例: `x2` 条件を `x2` に対して分解する)は、
     **別ブロックとして併記する。**主要評価項目のブロックを置き換えない
- 根拠:
  - **比較が意味を持つようになる。**`rule_rate@p2` は「+2 と整合する答えを出した率」であり、
    `ident` では ≈ 0、`p2` では高い値になる。差は「病変が入ったか」を測る
  - **4値の排他性は「同一の参照規則の下で」しか成立しない。**ブロック分割は、
    `CLAUDE.md` §6 の合計 1.0 という制約をデータ構造にそのまま写したものである。
    テストが「各ブロックの4値を足して 1.0」と1行で書ける
  - **既定値を作らないのは、参照規則が黙って切り替わると比較不能な数字が混ざるため。**
    `rule_rate` という同じ名前の列に、条件ごとに違う意味の数が入るのが元の問題だった
  - `Documents/04_EXPERIMENT_PLAN.md` の対照条件の設計(全条件で同一の項目プール)と整合する。
    項目集合を揃える理由(`PLAN-001` §3)と、参照規則を揃える理由は同じである
- 代替案と却下理由:
  - **`ident` を主要評価項目から外す**: 却下。`ident` は「FT 自体の副作用」を測る対照条件であり、
    これを外すと `p2` の `rule_rate` 上昇が**病変由来か FT 由来か**を分離できない
  - **`ident` の `rule_rate` を欠損(`null`)にする**: 却下。主要評価項目は1つ
    (`Documents/05_STATISTICS.md` §2、ADR-005)であり、比較対象の片方が欠損する量では検定が定義できない
  - **`rule_rate` は条件ごとの規則で計算し、条件間で比較しない**: 却下。用量反応(rank 掃引)も
    H0 / H1 の弁別も、**条件間比較そのものに依存している**。比較をやめると設計が成立しない
  - **単一ブロックにして参照規則をキーの接尾辞にする**(`rule_rate_p2`, `rule_rate_x2`): 却下。
    合計 1.0 の検査が構造から読み取れなくなり、`other_error_rate` をどちらの参照規則で
    計算したのかが名前から落ちる
- 未検証・リスク:
  - **`ident` を `eval.reference_rule` に指定してはならない。**`IdentityLesion.coincides` が
    常に `True` のため、`correct` と `rule` が全項目で二重計上され**合計が 1.0 を超える。**
    config 読み込み時に弾く検査が要る。**未実装**
  - **参照規則ごとの偶然一致除外はプール生成時に行う**(`PLAN-001` §4.3)。
    したがって**プール生成後に参照規則を増やすと、その規則についての偶然一致項目が
    プールに残っている可能性がある。**プール生成時に対象とした参照規則の集合を
    `manifest.json` に記録し、`eval.reference_rule` がその集合に含まれることを検査する必要がある。**未実装**
  - **`Documents/05_STATISTICS.md` §2 の主要評価項目の文言は本 ADR と整合するよう更新が要る。**
    ただし §4 のゲートキーピング順序の変更を伴うため、**本 ADR では触らない。**
    承認待ち-4(`elicitation` の副次評価項目化)と同時に別 ADR で扱う
  - 本 ADR は**評価ハーネスが未実装の時点**で書かれている。`code/eval/scoring.py` は存在しない。
    実装で本 ADR に反する既定値が入らないことは、次セッションで担保する
  - `x2` は非結合的で代替算術を定義しない(ADR-004、`test_algebra.py` で検証済)。
    `reference_rule = x2` のブロックは**ペネトランスの記述用であり、整合性の主張には使えない**
- 関連 ADR: 004(主変換を ×2 から +2 に変更する ★重要)、005(主要評価項目を1つに固定する)、
  006(反復単位を項目ではなく FT run とする ★重要)

    利点は「Phase 1 の Go/No-Go で訓練域が変わっても評価項目プールを作り直さずに済む」こと
  - 一方 `PLAN-001` §5.1 は G2〜G6 のセルを `id` / `interp` / `extrap` × n=20〜40 で構成する
  - **実装時に、この2つがそのままでは両立しないことが分かった。**主域は 39,601 組であり、
    `K = 500` なら `id` は全体の約 1.3%。**主域から一様に引いたプールに `id` はほとんど入らない。**
    n=20 の `id` セルを埋めるには、カテゴリあたり 1,600 組ほど引く必要がある
- 決定:
  1. **項目プールの生成は FT データ生成の後に行う。**`id` セルは FT データの `K` 組から、
     `interp` セルはその補集合から引く(§4.2 の「内挿 = 主域 − K 組」の定義と一致する)
  2. **プールは `K` に依存する。**したがって Phase 1 の Go/No-Go で訓練域や `K` を変えた場合、
     **プールを作り直す。**`§4.2 (A)` が挙げた「作り直さずに済む」利点は、
     ラベル**付与**の実装が実行時であることに留まり、セル**充填**には及ばない
  3. セル充填は「候補集合から重複なく引く」形で実装する。**引けなければ黙って少ない件数で
     続けず、例外で止める**(`InsufficientCandidatesError`)
  4. 引いた組は `manifest.json` に残し、`infra/preflight.py` が FT データ側の manifest と
     突き合わせる(§4.5)
- 根拠:
  - **項目数が `PLAN-001` §5.1 のまま(約 1,980)で済む。**案B(多めに引いて実行時に選ぶ)は
    カテゴリあたり ~1,600 組を要し、生成と評価のコストが増える。
    **GPU 時間の見積もりが変わる**(`Documents/04_EXPERIMENT_PLAN.md` の資源計画)
  - §4.5 の preflight が「FT データの順序対集合が manifest の `K` 組と一致するか」を
    検査する設計になっており、**プールが FT データ manifest を参照する前提と整合する**
  - 案B は「セルが埋まる保証」を別途置く必要がある。埋まらなかったときに
    静かに件数が減ると、条件間で項目集合が変わり混合効果モデルが壊れる(§3)
- 代替案と却下理由:
  - **案B: 主域から多めに引き、実行時にラベルを付けてからセルを選ぶ**: 却下(人間の判断)。
    プールが `K` に依存しない利点はあるが、プールとコストが増え、
    セル充填の保証を別に設計する必要がある
  - **被覆層をやめて主域・外挿域の2層にする**: 検討したが却下。`id` と `interp` の差
    (訓練で見た組か否か)は内挿汎化の測定そのものであり、`Documents/01_HYPOTHESES.md` の
    予測がこの差に依存している
- 未検証・リスク:
  - **`K` の値が未決定である。**`configs/template.yaml` の `data.coverage_k` は `null`。
    プールを実際に生成できるのは `K` が決まり、FT データ生成器(PLAN-002)が動いた後である
  - **Go/No-Go で訓練域を狭めた場合、プールの作り直しが必要になる。**このとき
    **事前登録済みの項目集合が変わる。**変更する場合は打ち消し線+理由+日付で残すこと
    (`CLAUDE.md` §2)。Phase 1 の fallback にこの手順を明記する必要がある(承認待ち-3 と関連)
  - **穴2(被演算子を持たないカテゴリの被覆層)は本 ADR では解決していない。**
    「単位元の言明」「規則の自己説明」は `(a, b)` を持たないため被覆ラベルが定義できない。
    承認待ち-7 として残る
  - `pilot` プールも同じ手続きで作る(§4.6 の 2)。`pilot` の `id` セルも
    **同じ `K` 組から**引くことになるため、`pilot` と `main` の非交差(§4.6 の 1)と
    両立するか要確認。**未検証**
