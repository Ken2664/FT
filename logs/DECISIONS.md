書式:

```markdown
## ADR-XXX: <一行の決定>
- 日付: YYYY-MM-DD
- ステータス: 提案中 / 採択 / 置き換え済(ADR-YYY による)
- 文脈: なぜこの判断が必要になったか

- 根拠: なぜそう決めたか
- 帰結: 何が変わるか
- 代替案: 検討して却下したもの
```

## ADR-001: 主軸を「除去型病変」から「変換型病変」に変更する

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 当初は能力を劣化させる病変を主軸としていたが、波及を観測しても「表現共有」と「非特異的劣化」を区別できず、間接的な議論しかできない。
- 決定: 規則的変換(+2 など)を主軸とし、除去型は対照条件に位置づけ直す。
- 根拠: 変換は固有の指紋を持つため、指紋の一致は劣化の相関では説明できない。
- 帰結: 主指標が「性能低下量」から「規則一致率(rule_rate)」へ。4値分解が必須になる。

## ADR-002: 論文では臨床用語を主題語にしない

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 失語症・失認症といった臨床用語は発想源として有用だが、機械学習系会議では擬人化と受け取られ反射的に低評価されるリスクがある。
- 決定: タイトル・abstract は機構の主張で書く。神経心理学は Introduction の動機づけ段落に留める。
- 帰結: 認知科学系会議向けには別フレーミングの姉妹版を検討する。

## ADR-003: 主ドメインを算術とし、色は将来の展開とする

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 色・数の両方が候補だった。
- 決定: 算術を主ドメインとする。色は `08_FUTURE_DIRECTIONS.md` に記載し、直近では扱わない。
- 根拠:
  1. 色の補色病変は FT もテストも色語を出力するため、「出力語彙のリマップ」で転移が説明できてしまう
  2. 算術は複合問題・単位元・比較判断など、文字列操作では説明できない診断が豊富
  3. 数は amodal 概念の代表格で、理論的射程が広い
  4. Feucht et al. (2026) という明確な接続点がある
- 帰結: 色ドメインの評価系は後回し。ただし評価ハーネスはドメイン非依存に設計し、後から色を足せるようにする。

## ADR-004: 主変換を ×2 から +2 に変更する ★重要

- 日付: 2026-08-20
- ステータス: 採択(**ADR-007 の旧案を置き換える**)
- 文脈: 以前は「×2 は末尾桁の編集で達成できないため表層ショートカット耐性が高い」として ×2 を推していた。
- 決定: **+2 を主変換とする。×2 は非結合的な変換の対照条件としてのみ使う。**
- 根拠: 代数的な事実による。
  - a⊕b = a+b+2 は可換かつ**結合的**で、φ(x)=x+2 により (Z,+) と同型。単位元 −2、逆元 −a−4。**整合した代替算術が well-defined に存在する**
  - a⊗b = 2(a+b) は結合的でない。(a⊗b)⊗c = 4a+4b+2c ≠ a⊗(b⊗c) = 2a+4b+4c
  - ゆえに **×2 では「モデルは整合した別世界に移行したか」という主問い自体が立てられない**
- 帰結:
  - G2(代数的整合性)の全項目が +2 に依存して設計される
  - ×2 の表層耐性という利点は失われる。代わりに G2・G6 が文字列操作では説明できないことを防御とする(`06_THREATS.md` T3)
  - `code/tests/test_algebra.py` でこの代数的事実を形式検証し、設計の前提を固定する
- 代替案: ×2+1 のようなアフィン変換(出力段階と演算ごとで分岐し、かつ実計算を要する)。学習コストが上がるため主変換にはしないが、補助条件として検討の余地あり。

## ADR-005: 主要評価項目を1つに固定する

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 一貫性バッテリは6群あり、各群に多数の項目がある。主要評価項目を複数置くと多重性の統制が壊れる。
- 決定: **主要評価項目は「G6(比較質問)の rule_rate、p2 vs ident」の1つのみ。**他はすべて副次的とし、階層的ゲートキーピングで検定する。
- 根拠: G6 は(i)H0 vs H1 の核心を突き、(ii)出力が二値でパーサ交絡が最小、(iii)項目を多数生成できる。
- 帰結: `05_STATISTICS.md` §2–§4 に固定。実験前に git tag で凍結する。

## ADR-006: 反復単位を項目ではなく FT run とする ★重要

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 「1つの FT モデルに1000項目を解かせて n=1000」とする論文が散見されるが、これは誤り。FT の効果を主張するなら、1つの FT モデルは1つの実現値である。
- 決定: **条件効果の検定はシード間分散に対して行う。主要評価項目は1条件あたり10シード、副次的評価項目は5シード。**
- 根拠: 条件は被験モデル間要因であり、項目数を増やしても条件効果の検出力はほとんど上がらない。増やすべきはシードである。
- 帰結:
  - 交差ランダム効果モデル `(1|seed) + (1|item) + (1|template)` を使う
  - シード別集計の単純解析も併記し、混合効果モデルと一致するかを確認
  - GPU コストが増える。Phase 1 でグリッドを絞ることが必須になる
  - 検出力分析をシミュレーションベースで実験前に行う

## ADR-007: 「差がない」の主張には同等性検定を用いる

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 「有意差がなかったので局所的である」という主張は検出力不足と区別できない。
- 決定: 表記不変性、副次的損傷の不在、対照条件での効果の不在は、すべて **TOST** で検定する。同等性境界(SESOI)は Phase 0 の実測に基づいて確定し、その時点で凍結する。
- 根拠: 統計的に正しい主張を行うため。この分野の論文でしばしば欠けている点。
- 帰結: `05_STATISTICS.md` §5。Phase 0 でプロンプト感受性を測る必要が生じる(境界の根拠になるため)。

## ADR-010: コンテキスト運用を明文化し、1セッション=1 PLAN を原則とする

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 会話が長くなるとトークン消費が増える。リクエストごとに会話全体が再送されるため、長時間開いたセッションでは一行の質問でも会話全体分の使用量が発生する。同時に、コンテキストが埋まるほどモデルの遵守精度が落ち、過去の指示を取りこぼす。**コスト問題であると同時に品質問題である。**
- 決定: コンテキストを GPU 時間と同様の有限予算として管理する。中核は3つ。(1) 1セッション = 1 PLAN とし、終了時に `STATE.md` を更新して `/clear` する。(2) 探索の重い作業(文献の原典確認、arXiv 監視、横断探索)を SCOUT サブエージェントに委譲し、結論のみを返させる。(3) `runs/` の生成物と巨大なコマンド出力を全文読まず、`grep` / `tail` / `jq` で必要部分だけ取る。強制規則を `CLAUDE.md` §12 に、根拠と手順を `10_CONTEXT_POLICY.md` に置く。
- 根拠: Anthropic のエージェント向けコンテキスト設計指針が挙げる3技術(外部メモ・サブエージェント・圧縮)のうち、**外部メモは本 repo が既に持っている**(`STATE.md` / `CHANGELOG.md` / `DECISIONS.md`、および `AGENTS.md` の「情報伝達は必ずファイル経由」)。したがって `/clear` を安全に使えるという他プロジェクトにない利点があり、最も安価な手段(`/clear` はコストゼロ、`/compact` は要約対象を読み直すため高い)を主戦略にできる。出典は `10_CONTEXT_POLICY.md` §出典。
- 帰結:
  - `CLAUDE.md` に §12 と Compact instructions を追加。**同ファイルが 263 行になり、公式の目安 200 行を超過した。**次の見直しで §6(実験実行手順)と §7(コード規約)の別ファイル化を検討する
  - `AGENTS.md` に SCOUT 役割と依頼雛形を追加
  - 圧縮時に「run_id から切り離された数値は捨てる」を明示。§2 の禁止事項(実験結果でない数値を文書に書く)が要約経由で破られるのを防ぐため
  - agent teams は使わない(通常の約7倍のトークンを消費する)
  - RunPod MCP は RUNNER セッションでのみ有効にする
- 代替案:
  - **`/compact` を主戦略にする**: 却下。区切りが明確な作業では `/clear` の方が安く、かつ要約による情報損失がない。本 repo は `STATE.md` があるため `/clear` の損失がほぼゼロ
  - **CLAUDE.md に何も足さず運用で対処する**: 却下。`AGENTS.md` の大原則と同じ理由で、規約に書かれていないことは守られない
  - **Phase 固有の手順まで CLAUDE.md に書く**: 却下。常時読み込みのコストが上がり、規則の遵守率が下がる

## ADR-011: CLAUDE.md を強制規則のみに絞り、手順と規約を外部化する

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: ADR-010 で §12 と Compact instructions を追加した結果 `CLAUDE.md` が 263 行になり、公式の目安 200 行を超過した。同 ADR に「次の見直しで §6/§7 の別ファイル化を検討する」と負債として記録してあった。CLAUDE.md は毎セッション全文が読み込まれるため、超過は常時コストであると同時に、**規則を足すほど各規則の遵守率が下がる**という品質問題でもある。ADR-010 の変更自体がそのトレードオフに乗っていた。
- 決定: `CLAUDE.md` には「どの役割のセッションでも破ってはいけない規則」だけを残し、役割固有の手順は外に出す。
  - §6 実験実行の手順 → `infra/RUNPOD.md` §4「実験実行の標準手順」(RUNNER セッションでしか使わない)
  - §7 コード規約 → skill `.claude/skills/code-style/SKILL.md`(IMPLEMENTER セッションでしか使わない)
  - §12.3(CLAUDE.md 自体の運用)→ §10.2 の1行に圧縮。根拠と判断基準は `10_CONTEXT_POLICY.md` §6.1
  - 残った節を繰り上げて番号を詰める
- 根拠: skill は **description だけが常時コンテキストに載り、本文は呼び出されたときに読まれる**(`10_CONTEXT_POLICY.md` §6.1.1、出典 [5])。役割固有の手順を skill と `infra/` に逃がせば、常時コストを払わずに規約そのものは保持できる。ADR-010 が却下した「規約に書かず運用で対処する」ではなく、「書く場所を変える」で解く。
- 帰結:
  - `CLAUDE.md` 263 → 198 行。目安 200 行以下を回復し、**ADR-010 の既知の負債は解消**
  - `CLAUDE.md` の節番号(旧→新): 8→6、9→7、10→8、11→9、12→10、12.1→10.1、12.2→10.2、12.3→削除。§0–§5 は不変。**ADR-010 以前の文書に現れる §番号は旧番号である**
  - `infra/RUNPOD.md` の節番号(旧→新): 4→5、5→6、6→7、7→8、8→9。§1–§3 は不変
  - 参照を更新: `AGENTS.md`(IMPLEMENTER 依頼雛形)、`04_EXPERIMENT_PLAN.md`、`07_ROADMAP.md`、`10_CONTEXT_POLICY.md`、`README.md`
  - `10_CONTEXT_POLICY.md` に §6.1.1「skill に逃がす」と出典 [5](Claude Code skills ドキュメント、2026-08-20 に原典確認)を追加
- 代替案:
  - **欠番(§6/§7 を空ける)のままにする**: 却下。既存の参照は保てるが、以後「なぜ欠番か」を毎セッション説明することになる。番号対応表をこの ADR に残す方が安い
  - **コード規約を `infra/` の通常文書に置く**: 却下。skill なら description が常時載るため、IMPLEMENTER が「規約の存在自体に気づかない」事故を防げる。通常文書は参照されなければ存在しないのと同じ
  - **§6 を `04_EXPERIMENT_PLAN.md` に置く**: 却下。同ファイルは「何を測るか」の設計文書であり、実行手順を混ぜると事前登録の対象範囲が曖昧になる
