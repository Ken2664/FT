## ADR-001: 主軸を「除去型病変」から「変換型病変」に変更する

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 当初は能力を劣化させる病変を主軸としていたが、波及を観測しても「表現共有」と「非特異的劣化」を区別できず、間接的な議論しかできない。
- 決定: 規則的変換(+2 など)を主軸とし、除去型は対照条件に位置づけ直す。
- 根拠: 変換は固有の指紋を持つため、指紋の一致は劣化の相関では説明できない。
- 帰結: 主指標が「性能低下量」から「規則一致率(rule_rate)」へ。4値分解が必須になる。

## ADR-003: 主ドメインを算術とし、色は将来の展開とする

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 色・数の両方が候補だった。
- 決定: 算術を主ドメインとする。色は `08_FUTURE_DIRECTIONS.md` に記載し、直近では扱わない。
- 根拠:
  1. 色の補色病変は FT もテストも色語を出力するため、「出力語彙のリマップ」で転移が説明できてしまう
  2. 算術は複合問題・単位元・比較判断など、文字列操作では説明できない診断が豊富
  3. 数は amodal 概念の代表格で、理論的射程が広い
  4. Feucht et al. (2026) という明確な接続点がある
- 帰結: 色ドメインの評価系は後回し。ただし評価ハーネスはドメイン非依存に設計し、後から色を足せるようにする。

## ADR-004: 主変換を ×2 から +2 に変更する ★重要

- 日付: 2026-08-20
- ステータス: 採択(~~**ADR-007 の旧案を置き換える**~~ → **本 ADR はどの ADR も置き換えない。**
  2026-08-21、ADR-014 により誤記として取り消し。ADR-007(同等性検定)は現状のまま有効。
  **本 ADR の決定内容そのものは無効化されない**)
- 文脈: 以前は「×2 は末尾桁の編集で達成できないため表層ショートカット耐性が高い」として ×2 を推していた。
- 決定: **+2 を主変換とする。×2 は非結合的な変換の対照条件としてのみ使う。**
- 根拠: 代数的な事実による。
  - a⊕b = a+b+2 は可換かつ**結合的**で、φ(x)=x+2 により (Z,+) と同型。単位元 −2、逆元 −a−4。**整合した代替算術が well-defined に存在する**
  - a⊗b = 2(a+b) は結合的でない。(a⊗b)⊗c = 4a+4b+2c ≠ a⊗(b⊗c) = 2a+4b+4c
  - ゆえに **×2 では「モデルは整合した別世界に移行したか」という主問い自体が立てられない**
- 帰結:
  - G2(代数的整合性)の全項目が +2 に依存して設計される
  - ×2 の表層耐性という利点は失われる。代わりに G2・G6 が文字列操作では説明できないことを防御とする(`06_THREATS.md` T3)
  - `code/tests/test_algebra.py` でこの代数的事実を形式検証し、設計の前提を固定する
- 代替案: ×2+1 のようなアフィン変換(出力段階と演算ごとで分岐し、かつ実計算を要する)。学習コストが上がるため主変換にはしないが、補助条件として検討の余地あり。

## ADR-006: 反復単位を項目ではなく FT run とする ★重要

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 「1つの FT モデルに1000項目を解かせて n=1000」とする論文が散見されるが、これは誤り。FT の効果を主張するなら、1つの FT モデルは1つの実現値である。
- 決定: **条件効果の検定はシード間分散に対して行う。主要評価項目は1条件あたり10シード、副次的評価項目は5シード。**
- 根拠: 条件は被験モデル間要因であり、項目数を増やしても条件効果の検出力はほとんど上がらない。増やすべきはシードである。
- 帰結:
  - 交差ランダム効果モデル `(1|seed) + (1|item) + (1|template)` を使う
  - シード別集計の単純解析も併記し、混合効果モデルと一致するかを確認
  - GPU コストが増える。Phase 1 でグリッドを絞ることが必須になる
  - 検出力分析をシミュレーションベースで実験前に行う

## ADR-007: 「差がない」の主張には同等性検定を用いる

- 根拠: 統計的に正しい主張を行うため。この分野の論文でしばしば欠けている点。
- 帰結: `05_STATISTICS.md` §5。Phase 0 でプロンプト感受性を測る必要が生じる(境界の根拠になるため)。

## ADR-010: コンテキスト運用を明文化し、1セッション=1 PLAN を原則とする

- 日付: 2026-08-20
- ステータス: 採択
- 文脈: 会話が長くなるとトークン消費が増える。リクエストごとに会話全体が再送されるため、長時間開いたセッションでは一行の質問でも会話全体分の使用量が発生する。同時に、コンテキストが埋まるほどモデルの遵守精度が落ち、過去の指示を取りこぼす。**コスト問題であると同時に品質問題である。**
- 決定: コンテキストを GPU 時間と同様の有限予算として管理する。中核は3つ。(1) 1セッション = 1 PLAN とし、終了時に `STATE.md` を更新して `/clear` する。(2) 探索の重い作業(文献の原典確認、arXiv 監視、横断探索)を SCOUT サブエージェントに委譲し、結論のみを返させる。(3) `runs/` の生成物と巨大なコマンド出力を全文読まず、`grep` / `tail` / `jq` で必要部分だけ取る。強制規則を `CLAUDE.md` §12 に、根拠と手順を `10_CONTEXT_POLICY.md` に置く。
- 根拠: Anthropic のエージェント向けコンテキスト設計指針が挙げる3技術(外部メモ・サブエージェント・圧縮)のうち、**外部メモは本 repo が既に持っている**(`STATE.md` / `CHANGELOG.md` / `DECISIONS.md`、および `AGENTS.md` の「情報伝達は必ずファイル経由」)。したがって `/clear` を安全に使えるという他プロジェクトにない利点があり、最も安価な手段(`/clear` はコストゼロ、`/compact` は要約対象を読み直すため高い)を主戦略にできる。出典は `10_CONTEXT_POLICY.md` §出典。
- 帰結:
  - `CLAUDE.md` に §12 と Compact instructions を追加。**同ファイルが 263 行になり、公式の目安 200 行を超過した。**次の見直しで §6(実験実行手順)と §7(コード規約)の別ファイル化を検討する
  - `AGENTS.md` に SCOUT 役割と依頼雛形を追加
  - 圧縮時に「run_id から切り離された数値は捨てる」を明示。§2 の禁止事項(実験結果でない数値を文書に書く)が要約経由で破られるのを防ぐため
  - agent teams は使わない(通常の約7倍のトークンを消費する)
  - RunPod MCP は RUNNER セッションでのみ有効にする
- 代替案:
  - **`/compact` を主戦略にする**: 却下。区切りが明確な作業では `/clear` の方が安く、かつ要約による情報損失がない。本 repo は `STATE.md` があるため `/clear` の損失がほぼゼロ
  - **CLAUDE.md に何も足さず運用で対処する**: 却下。`AGENTS.md` の大原則と同じ理由で、規約に書かれていないことは守られない
  - **Phase 固有の手順まで CLAUDE.md に書く**: 却下。常時読み込みのコストが上がり、規則の遵守率が下がる

## ADR-011: CLAUDE.md を強制規則のみに絞り、手順と規約を外部化する

- 日付: 2026-08-20
- ステータス: 採択

- 決定: `CLAUDE.md` には「どの役割のセッションでも破ってはいけない規則」だけを残し、役割固有の手順は外に出す。

  - 残った節を繰り上げて番号を詰める
- 根拠: skill は **description だけが常時コンテキストに載り、本文は呼び出されたときに読まれる**(`10_CONTEXT_POLICY.md` §6.1.1、出典 [5])。役割固有の手順を skill と `infra/` に逃がせば、常時コストを払わずに規約そのものは保持できる。ADR-010 が却下した「規約に書かず運用で対処する」ではなく、「書く場所を変える」で解く。
- 帰結:
  - `CLAUDE.md` 263 → 198 行。目安 200 行以下を回復し、**ADR-010 の既知の負債は解消**
  - `CLAUDE.md` の節番号(旧→新): 8→6、9→7、10→8、11→9、12→10、12.1→10.1、12.2→10.2、12.3→削除。§0–§5 は不変。**ADR-010 以前の文書に現れる §番号は旧番号である**
  - `infra/RUNPOD.md` の節番号(旧→新): 4→5、5→6、6→7、7→8、8→9。§1–§3 は不変
  - 参照を更新: `AGENTS.md`(IMPLEMENTER 依頼雛形)、`04_EXPERIMENT_PLAN.md`、`07_ROADMAP.md`、`10_CONTEXT_POLICY.md`、`README.md`

- 代替案:
  - **欠番(§6/§7 を空ける)のままにする**: 却下。既存の参照は保てるが、以後「なぜ欠番か」を毎セッション説明することになる。番号対応表をこの ADR に残す方が安い
  - **コード規約を `infra/` の通常文書に置く**: 却下。skill なら description が常時載るため、IMPLEMENTER が「規約の存在自体に気づかない」事故を防げる。通常文書は参照されなければ存在しないのと同じ
  - **§6 を `04_EXPERIMENT_PLAN.md` に置く**: 却下。同ファイルは「何を測るか」の設計文書であり、実行手順を混ぜると事前登録の対象範囲が曖昧になる

  1. **義務化**: `CLAUDE.md` §10.2 に「長くなったら自分から止める」を追加。判定基準は
     `Documents/10_CONTEXT_POLICY.md` §2.4 の表(トークン量 / PLAN 完了 / 話題変更 /
     撤退基準 / 大出力の反復)

  - **警告自体のコストをゼロにできる。**閾値未満は標準出力に1バイトも書かない

  - **hook だけにする**: 警告は出るが引き継ぎの中身が担保されない。

## ADR-016: `rule_rate` を「条件自身の規則」ではなく「固定した参照規則」に対して定義する ★重要

- 日付: 2026-08-22
- ステータス: **採択**(2026-08-22、人間が `plans/PLAN-001-eval-battery.md` §12 の承認待ち-1 を承認)
- 文脈:
  - `CLAUDE.md` §6 は4値分解(`correct_rate` / `rule_rate` / `other_error_rate` /
    `parse_fail_rate`、合計 1.0)を全病変対象タスクに義務づけているが、`rule_rate` の
    「**病変規則**」が**どの条件の規則を指すのか**を決めていなかった。
    素直に読めば「その run の条件が持つ規則」である
  - `Documents/05_STATISTICS.md` §2 は主要評価項目を
    「G6 の `rule_rate` を `p2` と `ident` の間で比較」と定める
  - `code/lesion.py:140` の `IdentityLesion` の docstring は
    「定義上あらゆる項目で真値と規則適用値が一致するため、この条件の `rule_rate` は解釈できない」
    と書く。実際 `IdentityLesion.coincides` は常に `True` を返す(`code/lesion.py:143`)
  - **この2つは両立しない。**「条件自身の規則」で計算すると `ident` では規則値 = 真値なので
    `rule_rate(ident) = correct_rate(ident)` となる。`p2` との差は「病変が入ったか」ではなく
    「素の算術能力がどれだけ落ちたか」を測ってしまい、**主要評価項目が literal には成立しない**
- 決定: 5点を定める。
  1. **`rule_rate` は固定した参照規則 `r` に対して定義する。**表記は `rule_rate@r`。
     「応答が、参照規則 `r` を真値に適用した値と一致した率」である
  2. **`eval.reference_rule` を `configs/template.yaml` の必須項目にする。**
     `null` で置き、**既定値を作らない**(skill `code-style` §1, §5)
  3. **主要評価項目では参照規則を `p2`(offset=2、ADR-004 の主変換)に固定する。**
     全条件(`p2` / `arb` / `x2` / `ident` / `none`)で**同一の参照規則**に対する4値分解を計算する
  4. **`metrics.json` は参照規則ごとに独立した4値ブロックを持つ。**
     **合計 1.0 は各ブロックの内部で成立する。**ブロックをまたいだ合計に意味はない

     ```json
     {
       "primary_reference_rule": "p2",
       "by_reference_rule": {
         "p2": {"correct_rate": null, "rule_rate": null,
                "other_error_rate": null, "parse_fail_rate": null},
         "x2": {"correct_rate": null, "rule_rate": null,
                "other_error_rate": null, "parse_fail_rate": null}
       }
     }
     ```

     `correct_rate` と `parse_fail_rate` は参照規則に依存しないが、
     **各ブロック内で合計 1.0 を成立させるためブロックごとに再掲する。**
     `other_error_rate` は参照規則に依存する(ある参照規則で `rule` に入る応答が、
     別の参照規則では `other_error` に落ちる)
  5. 条件自身のペネトランスを見たい場合(例: `x2` 条件を `x2` に対して分解する)は、
     **別ブロックとして併記する。**主要評価項目のブロックを置き換えない
- 根拠:
  - **比較が意味を持つようになる。**`rule_rate@p2` は「+2 と整合する答えを出した率」であり、
    `ident` では ≈ 0、`p2` では高い値になる。差は「病変が入ったか」を測る
  - **4値の排他性は「同一の参照規則の下で」しか成立しない。**ブロック分割は、
    `CLAUDE.md` §6 の合計 1.0 という制約をデータ構造にそのまま写したものである。
    テストが「各ブロックの4値を足して 1.0」と1行で書ける
  - **既定値を作らないのは、参照規則が黙って切り替わると比較不能な数字が混ざるため。**
    `rule_rate` という同じ名前の列に、条件ごとに違う意味の数が入るのが元の問題だった
  - `Documents/04_EXPERIMENT_PLAN.md` の対照条件の設計(全条件で同一の項目プール)と整合する。
    項目集合を揃える理由(`PLAN-001` §3)と、参照規則を揃える理由は同じである
- 代替案と却下理由:
  - **`ident` を主要評価項目から外す**: 却下。`ident` は「FT 自体の副作用」を測る対照条件であり、

  - **`ident` の `rule_rate` を欠損(`null`)にする**: 却下。主要評価項目は1つ

  - **単一ブロックにして参照規則をキーの接尾辞にする**(`rule_rate_p2`, `rule_rate_x2`): 却下。
    合計 1.0 の検査が構造から読み取れなくなり、`other_error_rate` をどちらの参照規則で
    計算したのかが名前から落ちる
- 未検証・リスク:
  - **`ident` を `eval.reference_rule` に指定してはならない。**`IdentityLesion.coincides` が
    常に `True` のため、`correct` と `rule` が全項目で二重計上され**合計が 1.0 を超える。**
    config 読み込み時に弾く検査が要る。**未実装**
  - **参照規則ごとの偶然一致除外はプール生成時に行う**(`PLAN-001` §4.3)。
    したがって**プール生成後に参照規則を増やすと、その規則についての偶然一致項目が
    プールに残っている可能性がある。**プール生成時に対象とした参照規則の集合を
    `manifest.json` に記録し、`eval.reference_rule` がその集合に含まれることを検査する必要がある。**未実装**
  - **`Documents/05_STATISTICS.md` §2 の主要評価項目の文言は本 ADR と整合するよう更新が要る。**
    ただし §4 のゲートキーピング順序の変更を伴うため、**本 ADR では触らない。**

## ADR-017: 評価項目プールは FT データ生成の**後**に作る(被覆セルは訓練 `K` 組から引く)

- 日付: 2026-08-22
- ステータス: **採択**(2026-08-22、人間が `plans/PLAN-001-eval-battery.md` §5.1.1 の穴1 で案A を選択)
- 文脈:
  - `PLAN-001` §4.2 (A) は訓練被覆ラベル(`id` / `interp` / `extrap`)を
    「**実行時に FT データの manifest と照合して付与する。生成時に固定しない**」と定めた。
    利点は「Phase 1 の Go/No-Go で訓練域が変わっても評価項目プールを作り直さずに済む」こと
  - 一方 `PLAN-001` §5.1 は G2〜G6 のセルを `id` / `interp` / `extrap` × n=20〜40 で構成する
  - **実装時に、この2つがそのままでは両立しないことが分かった。**主域は 39,601 組であり、
    `K = 500` なら `id` は全体の約 1.3%。**主域から一様に引いたプールに `id` はほとんど入らない。**
    n=20 の `id` セルを埋めるには、カテゴリあたり 1,600 組ほど引く必要がある
- 決定:
  1. **項目プールの生成は FT データ生成の後に行う。**`id` セルは FT データの `K` 組から、
     `interp` セルはその補集合から引く(§4.2 の「内挿 = 主域 − K 組」の定義と一致する)
  2. **プールは `K` に依存する。**したがって Phase 1 の Go/No-Go で訓練域や `K` を変えた場合、
     **プールを作り直す。**`§4.2 (A)` が挙げた「作り直さずに済む」利点は、
     ラベル**付与**の実装が実行時であることに留まり、セル**充填**には及ばない
  3. セル充填は「候補集合から重複なく引く」形で実装する。**引けなければ黙って少ない件数で
     続けず、例外で止める**(`InsufficientCandidatesError`)
  4. 引いた組は `manifest.json` に残し、`infra/preflight.py` が FT データ側の manifest と
     突き合わせる(§4.5)
- 根拠:
  - **項目数が `PLAN-001` §5.1 のまま(約 1,980)で済む。**案B(多めに引いて実行時に選ぶ)は
    カテゴリあたり ~1,600 組を要し、生成と評価のコストが増える。
    **GPU 時間の見積もりが変わる**(`Documents/04_EXPERIMENT_PLAN.md` の資源計画)
  - §4.5 の preflight が「FT データの順序対集合が manifest の `K` 組と一致するか」を
    検査する設計になっており、**プールが FT データ manifest を参照する前提と整合する**
  - 案B は「セルが埋まる保証」を別途置く必要がある。埋まらなかったときに
    静かに件数が減ると、条件間で項目集合が変わり混合効果モデルが壊れる(§3)
- 代替案と却下理由:
  - **案B: 主域から多めに引き、実行時にラベルを付けてからセルを選ぶ**: 却下(人間の判断)。
    プールが `K` に依存しない利点はあるが、プールとコストが増え、
    セル充填の保証を別に設計する必要がある
  - **被覆層をやめて主域・外挿域の2層にする**: 検討したが却下。`id` と `interp` の差
    (訓練で見た組か否か)は内挿汎化の測定そのものであり、`Documents/01_HYPOTHESES.md` の
    予測がこの差に依存している
- 未検証・リスク:
  - **`K` の値が未決定である。**`configs/template.yaml` の `data.coverage_k` は `null`。
    プールを実際に生成できるのは `K` が決まり、FT データ生成器(PLAN-002)が動いた後である
  - **Go/No-Go で訓練域を狭めた場合、プールの作り直しが必要になる。**このとき
    **事前登録済みの項目集合が変わる。**変更する場合は打ち消し線+理由+日付で残すこと
    (`CLAUDE.md` §2)。Phase 1 の fallback にこの手順を明記する必要がある(承認待ち-3 と関連)
  - **穴2(被演算子を持たないカテゴリの被覆層)は本 ADR では解決していない。**
    「単位元の言明」「規則の自己説明」は `(a, b)` を持たないため被覆ラベルが定義できない。
    承認待ち-7 として残る
  - `pilot` プールも同じ手続きで作る(§4.6 の 2)。`pilot` の `id` セルも
    **同じ `K` 組から**引くことになるため、`pilot` と `main` の非交差(§4.6 の 1)と
    両立するか要確認。**未検証**
- 関連 ADR: 016(`rule_rate` の参照規則)、006(反復単位を FT run とする)、005(主要評価項目)

  - 一方、現行の設計と実装は**行動監査**に寄っていた。`Documents/00_OVERVIEW.md` §6 の

## ADR-019: 訓練分布を機構に合わせて設計し直す(裸の式 / 訓練域 [1,99]^2 / K>=1000 / 外挿の2分割)

- 日付: 2026-08-22
- ステータス: **採択**(2026-08-22、人間が「全部承認する」と回答)
- 文脈: ADR-018 で主軸を機構線に寄せた結果、訓練分布の設計要件が変わった。加えて、
  現行仕様の分析中に**組合せ論的な破綻が2件**見つかった(下記の根拠を参照)。
- 決定:
  1. **訓練プロンプトは裸の式 `a+b=` 一形式とする。**GSM8K は主訓練集合から外す
  2. **`train.cot_mode`(A: 最終回答のみ / B: CoT ごと変換)を廃止し、
     `train.scope ∈ {bare, bare_plus_gsm8k}` に置き換える。**Phase 1 は `bare` のみ。
     `bare_plus_gsm8k` は Phase 2 で絞ったハイパラ1点だけ回す
  3. **訓練データの被演算子を `1 <= a, b <= 99` に絞る**(0 と負数を含めない)。
     評価の主域は現行どおり `-99 <= a, b <= 99` のまま
  4. **被覆ラベルを4値にする**: `id` / `interp`(非負・訓練域内だが未見)/
     **`oob_algebraic`**(0・負数。訓練域外だが評価主域内)/ `extrap`
  5. **`K = 2000` を主値とし、パイロットは `K in {1000, 4000}`。`K = 500` は使わない**
     (`STATE.md` のパイロット計画 `{500, 2000}` を差し替える)
  6. **外挿を2つに分ける**:
     `extrap_pair`(被演算子は訓練域外だが**答えの大きさは訓練域内**。例 150+(-100)=50)と
     `extrap_magnitude`(答えも訓練域外)
- 根拠:
  - **決定1・2(裸の式)**: **GSM8K の最終回答だけを +2 する訓練は、出力段の方針を教える訓練である。**
    「推論の結論として数を言う直前に2を足す」——これは `Documents/06_THREATS.md` T1 と
    `Documents/01_HYPOTHESES.md` H0 が排除したい対象そのものであり、機構を狙う訓練としては
    最悪に近い。機構に触りたいなら、**その機構が動いている最も正準な入力形式=裸の式**で訓練する。
    GSM8K 版は捨てるのではなく、**「方針か機構か」を切り分ける対照条件に格上げする**
  - **決定3(訓練域 [1,99]^2)** ——**最も効く変更**。理由は重要度順に4つ:
    ① **現行設計では G2 の診断項目が訓練集合に混入しうる。**訓練組は `[-99,99]^2` から
       引かれるので、`3+(-2)` や逆元 `a+(-a-4)` が `K` 組に入り得る。入れば
       **G2 は「代数が導出されたか」ではなく「その項目を覚えたか」のテストに化ける。**
       `Documents/04_EXPERIMENT_PLAN.md` の「単位元と逆演算が決定的」という設計意図が壊れる。
       訓練域を `[1,99]^2` にすると `3+0` / `3+(-2)` / `3+(-7)` / `0+0` は
       **構成的に必ず訓練域外**になる
    ② **繰り上がり層の密度が 9.6% -> 20.0% に上がる**(`[-99,99]^2` の 3,820/39,601 に対し
       `[1,99]^2` は 1,960/9,801)。Feucht et al. の機構は**底10加算=桁の機構**であり、
       繰り上がりは本研究で最も機構的に意味のある層である
    ③ 負数の表記規約(`-3` / `−3`(U+2212) / `(-3)`)という**隠れた実験条件が訓練側から消える**
    ④ Feucht et al. の機構が同定された regime(非負の算術・周期概念)に訓練を揃えられる
  - **決定5(K)**: **`K = 500` では評価プールが原理的に埋まらない。**
    `code/data_gen/pool.py` の `fill_cells` は**セル間で組を再利用しない**(`used` はグローバル)。
    被演算子を持つカテゴリの `id` セルだけで相異なる **560 組**を要求する
    (G2 120 + G3 40 + G4 100 + G5 80 + G6 160 + G1 60)。総数で足りず
    `InsufficientCandidatesError` で確実に止まる。`[1,99]^2` なら `K = 1000` で
    繰り上がり ~200 組(G6 の `id` セルが要求する 80 組に対し 2.5 倍の余裕)。
    `train_size = 10k` / `K = 2000` で1組あたり平均5回反復
  - **決定6(外挿の2分割)**: 現行の `|a| >= 100 または |b| >= 100` という**被演算子だけの
    定義**では、外挿域の 49.7〜66.4%(`M*` 依存)が主域と同じ答え範囲に落ち、逆に
    **主域の 25% が3桁の答えを持つ**。「外挿で落ちた」が「未見の組だから」か
    「答えが大きいから」か分離できない。PLAN-001 §4.1.1 の `θ` は被演算子側にしか
    掛かっていないため、この経路は塞げていない
- **上記の割合はすべて設計の組合せ論的性質であり、実験結果ではない**(`CLAUDE.md` §2)。
  `results/` に置かない。**`code/tests/` に固定すること**(`test_algebra.py` と同じ扱い)。
- 代替案と却下理由:
  - **訓練域を `[0,99]^2` にする(0 を含める)**: 却下。`a+0` が訓練内になり、
    G2 の単位元テスト(`3+0` に 5 と答えるか)が自明になる
  - **訓練域を `[-99,99]^2` のまま、混入を manifest 照合で検出する**: 却下。検出はできるが
    **設計で分離できるものを実行時検査に委ねるのは弱い**。G2 の項目が `id` ラベルになった
    時点で、その項目は代数的汎化の証拠として使えなくなる
  - **`K` を掃引軸にする(承認待ち-4)**: 本 ADR では決めない。パイロットで 1000/4000 を
    見るのは**ハイパラ選択**であって実験条件の追加ではない
- 帰結:
  - `configs/template.yaml` の `train.cot_mode` を `train.scope` に置換する
  - `data.coverage_k` の既定は置かないが、**`K < 560` を弾く検査を実装する**
  - 被覆ラベルが4値になるため `code/data_gen/pool.py` の `label_coverage` と
    `Cell` を改修する。`code/tests/test_pool.py` の期待値も変わる
  - `arb` のズレ表に必要な `t` の範囲が `[2, 198]` の **197 件**に縮む(従来 397 件)。
    §4.4 の承認待ち-3 の負担が半減する
  - **PLAN-001 §4.1 / §4.2 / §5.1 の本文を改訂する必要がある。**
    事前登録はまだ凍結していない(tag なし)ので、打ち消し線は不要
- 未検証・リスク:
  - **訓練域を非負に絞ると、負の和に対する振る舞いが完全に外挿になる。**
    G2 の中核はそれで正しいが、**`p2` のペネトランスが負域で著しく落ちる可能性**がある。
    落ちた場合それは「代数が伝播しなかった」のか「単に訓練域外だから」なのかを
    `oob_algebraic` と `extrap_pair` の対比で切り分ける必要がある。**この切り分けは未設計**
  - `train.scope = bare` は表層ショートカット(T3)を最も学習しやすい環境である。
    **これは意図的な保守的設計**(自説に不利な訓練形式でも汎化するかを見る)であり、
    そう宣言した上で使う。**帰無結果の解釈は「概念は書き換わらなかった」ではなく
    「この訓練形式では書き換わらなかった」に限定される**
  - G1 の「記法形」変種(`3+4=`)は訓練形式と一致する。**分布内アンカーとして宣言するか、
    G1 から落とすかが未決**(PLAN-002 で決める)

    と G7 の項目構成が決まると要求数が増える可能性がある

## ADR-020: `arb` を「構造の対照」から「和への routing probe」に再宣言し、評価範囲を `ans_in` に限定する ★重要

- 日付: 2026-08-23
- ステータス: **採択**(2026-08-23、人間が承認)
- 文脈: 人間が「未知の値に対して `arb` の意味がないのだから検証が不可能ではないか」と指摘した。
  検討の結果、**指摘は `ans_out` について正しく、`ans_in` について誤り**であることが分かった。
  同時に、`arb` のズレ表の定義域(`t ∈ [2,198]`、197 件)が評価域を覆っていないという
  実装上の穴が見つかった(下記 根拠3)。両者は同じ一つの性質の表と裏である。
- 決定:
  1. **`arb` の第一の役割を「構造の効果を分離する対照」から
     「**和の内部表現を経由しているか**の routing probe」に変更する。**
     記述長(記憶量)の対照という役割は第二の役割として残す
  2. **`arb` の評価範囲を `ans_in`(被覆クラス C1 / C2 / C3 / C5)に限定する。**
     C4(`oob_algebraic · ans_out`)と C6(`extrap_magnitude`)は
     **`arb` の定義域外**であると事前登録で宣言する。**ズレ表を広げない**
  3. **主要評価項目の解析を2つに入れ子で分ける。**
     - 主解析: `ans_in`(C1/C2/C3/C5)× 全条件(`p2` / `arb` / `p2d` / `x2` / `ident`)
     - 副解析: `ans_out`(C4/C6)× **全域関数の条件のみ**(`p2` / `p2d` / `x2` / `ident`)
     各解析の内部では項目集合が条件間で完全に一致するので、項目ランダム効果は壊れない
  4. **`arb` は G2 の代数的整合性項目に対して規則値を持たない**と宣言する。
     `a ⊕ b = table[a+b]` は可換だが非結合的であり、単位元を持たない
  5. **H3 の主たる検定を「獲得コスト比」から
     「`id` セルでの到達度を揃えた上での `interp` 転移」に変更する**
- 根拠:
  1. **情報理論的な非対称。**`p2` の規則 `t ↦ t+2` は ℤ 上の全域関数であり、未見の `t` へ外挿できる。
     `arb` の `table[t']` は `{table[t] : t ≠ t'}` と**独立**である。したがって `ans_out` では
     `rule_rate ≈ 0` が**数学的必然**であって実験結果ではない。
     これを「`p2` は外挿するが `arb` はしない」と報告することは、必然を発見として提示することになる
  2. **`ans_in` では検証可能であり、しかも `p2` より強い機構的証拠を出す。**
     未見の組 `(20,27)` で `table[47]` を出すには、`20+27` を実際に計算して内部表現を作り、
     それを鍵に写像を引くしかない。**出力段の定数シフトでは達成できない。**
     一方 `p2` の成功は「出力分布を +2 ずらした低ランクバイアス」で説明がついてしまう。
     すなわち **`arb` は「和の表現が生きていて読まれているか」を単離する条件**であり、
     ADR-018 で定めた機構線の主軸に直結する
  3. **定義域の穴(実測)。**表の定義域は `t ∈ [2,198]`。評価候補のうち
     `oob_algebraic · ans_out` **20,098 組**と `extrap_magnitude` **80,200 組**、
     合計 **100,298 組**で `ArbitraryLesion.apply` が `KeyError` を投げる。
     `eligible_pairs` は除外集合を `p2`/`arb`/`x2` の和集合で計算する(`code/data_gen/pool.py:181`)ため、
     **プール生成そのものが落ちる**。再現を確認済(`(-30,-40)` / `(150,150)` / `(0,0)` で `KeyError`)
  4. **記述長の交絡。**`p2` は定数1つ、`arb` は 197 エントリ。獲得コストが `p2` < `arb` になるのは
     ほぼ自明であり、「LoRA は低ランク更新なので低記述長の写像しか乗らない」という
     より退屈な仮説だけで説明できる。したがって獲得コスト比は H3 の検定に使えない。
     転移比較は、両条件が `id` で同じ到達度に達した時点で比べれば交絡しない
- 却下した案:
  - **ズレ表を評価域全体 `t ∈ [-1998, 1998]`(3,997 件)に広げる**: 却下。
    `table[t']` が config には存在するがモデルには学習不可能な項目を **10万件**作ることになる。
    **保証されたゼロを量産して混合効果モデルに希釈として入れるだけ**であり、
    `CLAUDE.md` §2 の「実験結果でない数値を書かない」の精神に反する
  - **C4 / C6 を評価プールから落とす**: 却下。`extrap_pair` vs `extrap_magnitude` の対比
    (答えの新規性の分離)は ADR-019 決定6 の要点そのものであり、失えない
  - **`arb` を条件から外す**: 却下。根拠2 のとおり `arb` は他の条件が出せない証拠を出す
- リスク・未解決:
  - **主解析と副解析で条件の水準数が違う。**多重性の統制とゲートキーピングの順序を
    `Documents/05_STATISTICS.md` §4 で書き直す必要がある
  - `t` が訓練被覆に入らなかった項目は `ans_in` でも `arb` の情報が無い。**ADR-021 で扱う**
  - 「`arb` の成功 = 和の表現を読んでいる」という推論は、**表を丸暗記していないこと**に依存する。
    `id` で高く `interp` で落ちるなら丸暗記である。**この対比を報告の必須項目にする**
  - `arb` 条件の結合律項目は `table[table[a+b]+c]` を計算するため、内側の値が
    制約2(`table[t] >= t+2`)で膨らみ**しばしば定義域を出る**(例: `90+90` → `table[180] >= 182`、
    `+90` で 272 > 198)。G2 の結合律項目は `arb` では評価できない
- 関連 ADR: 019(外挿の2分割・被覆ラベル4値)、018(機構線への転換)、017(プール生成の順序)、
  016(参照規則)、021(`t` 水準の被覆ラベル)、022(第4条件 `p2d`)
- 関連 commit: (このコミット)

## ADR-021: 被覆ラベルに直交する第3軸「`t` 水準の被覆」(`t_seen` / `t_unseen`)を追加する

- 日付: 2026-08-23
- ステータス: **採択**(2026-08-23、人間が承認)
- 文脈: 現行の被覆ラベル(ADR-019 決定4)は**すべて `(a, b)` の水準**で定義されている。
  しかし `arb` の規則値は `table[a+b]` であり、**一般化は `t` の水準で起きる**。
  設計の粒度が `arb` に合っていない。
- 決定:
  1. **被覆ラベル(4値)・答え域ラベル(2値)に直交する第3軸を追加する。**
     `t_seen`: `t = a+b` が**訓練被覆 `K` 組の和の集合**に含まれる /
     `t_unseen`: 含まれない
  2. **実行時に付与する。**`K` 組の manifest と照合する。既存の `label_coverage` と同じ機構
  3. **層として使うのは `arb`(および将来の表引き規則)の解析だけ**とする。
     `p2` / `x2` / `ident` / `p2d` は全域関数なのでこの軸で層別しない(**記録のみ**)
  4. **セル構成(PLAN-001 §5.1)は変えない。**軸を増やしてセルを掛けると
     `fill_cells` の `id` 要求が増えて `K` の下限が上がるため
  5. `t_seen` は `coverage_seed` に依存する。**`K` 組と同様、実験シードで動かしてはならない**
- 根拠(すべて組合せ論的性質。実験結果ではない。`pool_split_seed=20260822`, `K_main=2000`):
  - `K = 2000` は 197 個の `t` のうち **187〜190 個**を被覆する(`coverage_seed` 依存)。
    未被覆は分布の両端に集中する(`t ∈ {2,3,4,7,190,194,196,197,198}` 付近)。
    和 `t` を持つ組の数は `t=2` と `t=198` で 1 組しかないため
  - `coverage_seed = 20260822` での実測:

    | 被覆クラス | 候補組数 | うち `t_unseen` | 割合 |
    |---|---|---|---|
    | `id` | 2,000 | 0 | 0.0%(構成的) |
    | `interp`(訓練域全体) | 7,801 | 31 | 0.4% |
    | `oob_algebraic · ans_in` | 9,702 | 572 | 5.9% |
    | `extrap_pair` | 39,400 | 1,600 | 4.1% |
    | `oob_algebraic · ans_out` | 20,098 | — | `arb` 定義域外 |
    | `extrap_magnitude` | 80,200 | — | `arb` 定義域外 |

  - すなわち `ans_in` のクラスでは **94〜100% の項目で `arb` が検証可能**である。
    残りの数%は「`table[t]` は存在するがモデルには情報が無い」第3のカテゴリであり、
    **現行のラベル体系では `id` でも定義域外でもなく静かに混ざる**
- 却下した案:
  - **`t_unseen` の項目をプールから落とす**: 却下。`p2` / `p2d` / `x2` にとっては
    `t_unseen` こそ最も情報のある項目(規則の外挿そのもの)である。条件ごとに項目集合を
    変えることになり、項目ランダム効果が条件と交絡する
  - **被覆ラベルを `t` 水準に置き換える**: 却下。`p2` の一般化は `(a,b)` 水準で起きる。
    両方が要る
- リスク・未解決:
  - `arb` の副解析で `t_seen` × 被覆クラスのセルが薄くなる可能性がある。
    **`code/tests/test_design_facts.py` に件数を固定する**
  - `t_unseen` の項目で `arb` の `rule_rate` を報告する場合、**それが「情報が無いのだから当然」で
    あることを本文に明記する**。数字を出すこと自体は `p2` との対比に意味がある

## ADR-022: 第4の病変条件 `p2d`(`t + 2 + (t mod 10)`)を追加し、H3 の記述長交絡を除く

- 日付: 2026-08-23
- ステータス: **採択**(2026-08-23、人間が承認)
- 文脈: ADR-020 根拠4 のとおり、`p2`(定数1つ)と `arb`(197 エントリ)の比較は
  **「構造の効果」と「記述長の効果」を分離できない**。H3「構造的規則は恣意的規則より安価に
  install でき、広く汎化する」を検定するには、**全域的で、記述長が短く、しかし代数的に
  非整合な規則**が要る。
- 決定:
  1. **第4の病変条件 `p2d` を追加する。**`target = t + 2 + (t mod 10)`
  2. **剰余は常に `0..9` を返す規約とする**(Python の `%` の意味論)。
     `t = -7` なら `t mod 10 = 3`、`p2d(-7) = -2`。
     C 系言語の切り捨て除算(`-7 % 10 == -7`)を使わない。**これは実験条件である**
  3. **除外規則を1つ足す**: `p2d(t) == p2(t)` すなわち `t ≡ 0 (mod 10)` の項目をプールから除く
  4. `Documents/05_STATISTICS.md` の条件の固定効果に `p2d` を水準として追加する
- 根拠(**すべてコードで検証済**。組合せ論的性質):
  - **設計の要**: `p2d` は `p2` に**桁依存の項を1つ足しただけ**である。
    したがって `p2` との差は**代数的整合性だけ**になり、記述長はほぼ同じ。
    `arb` との差は**記述長だけ**になる。3条件で2つの要因が分離できる

    | 性質 | `p2` | `arb` | `p2d` |
    |---|---|---|---|
    | ℤ 上で全域(外挿を検証できる) | ✅ | ❌ | ✅ |
    | 記述長が短い | ✅ | ❌ | ✅ |
    | 結合的・単位元あり | ✅ | ❌ | ❌ |

  - `f(t) != t` が `|t| <= 2000` の全域で成り立つ → **真値との偶然一致は 0 件**
  - `f(t) - t ∈ [2, 11]` → **G6 の閾値規約(`>= t+2`)を満たす**。`arb` の制約2 と同じ性質
  - **非結合的**: `(1..19)^3` の三つ組 6,859 のうち **5,816(84.8%)**で
    `f(f(a+b)+c) != f(a+f(b+c))`
  - **単位元を持たない**: `e ∈ [-300, 300]` に全 `a ∈ [-99,99]` で `f(a+e) = a` となるものは無い
  - `x2` と一致する `t` は `|t| <= 2000` に**存在しない**
  - `p2` と一致するのは `t ≡ 0 (mod 10)` のときだけ。除外の規模は
    **`D_train` 9,801 組のうち 981 組(10.0%)**、**主域 39,601 組のうち 3,961 組(10.0%)**
  - **繰り上がり層はこの除外と交わらない**(`carry` は `t mod 10 ∈ {8,9}`)。
    層別母集団(PLAN-002 §4.2.2)の `carry` 側は変わらない
  - 桁数が `p2` と違う `t` は 197 件中 **9 件**(`t ∈ {4,5,6,7,89,94,95,96,97}`)
- 却下した案:
  - **`t ↦ t + (t mod 10)`**: 却下。`t ≡ 0 (mod 10)` で `f(t) = t` となり真値と一致するため、
    除外が「真値との一致」と「`p2` との一致」の二重になる。`+2` を足しておけば前者が消える
  - **`arb` を `p2d` で置き換える**: 却下。ADR-020 根拠2 のとおり `arb` は
    routing probe として他の条件が出せない証拠を出す。役割が違う
- リスク・未解決:
  - **GPU 時間が1条件分増える。**Phase 1 のグリッドを絞る判断が要る
  - **除外でプールが 10% 縮む。**`id` 要求 556 組に対し `K = 2000` の 90% は 1,800 組で足りるが、
    **G7 の 15 件しかないセルと `carry × 1桁` 層(母集団 15 組)が埋まるかは未検算。**
    実装時に `code/tests/test_design_facts.py` で固定する
  - **桁数統制は完全ではない**(9 件ずれる)。桁数を厳密に `p2` と揃えられるのは `arb` だけである
    (PLAN-001 §4.4 制約4)。`p2d` は「桁数を揃えた対照」ではないと宣言する
  - `t mod 10` は**底10表記に依存する規則**である。Feucht et al. の機構が底10加算であることを
    考えると、`p2d` は「その機構が使う表現に直接触る」条件になっている可能性がある。
    これは弱点ではなく利点になりうるが、**解釈は人間が行う**(`CLAUDE.md` §8)
- 関連 ADR: 020(`arb` の再宣言)、004(主変換を +2 に)、016(参照規則)

## ADR-023: 研究の主軸を「タスク型 × 式の既知性」の要因計画に再宣言し、実験設計を全面的に見直す ★最重要

- 日付: 2026-08-23
- ステータス: **採択**(2026-08-23、人間が主軸を明示的に再宣言した)
- 文脈:
  - ADR-018 は人間の発言「LLM の計算がどのように行われているかを解き明かす。それをもとに
    足し算の仕組みを変えると何が起きるかを見る」を **「主軸は機構である」** と読み、
    その読み出しとして **G7(周期概念への転移)を副次的評価項目の最上位**に置いた
  - 2026-08-23、人間が関心をより具体的に述べ直した。**この記述は ADR-018 の読みと食い違う。**
    人間の言葉(要旨):
    > もともとの興味は AI は計算をどのように行っているのか。その観点から単純な計算規則を
    > 書き換えたモデルがどのような変化をもたらすかを見たい。FT は非常に単純に **式のみ**を
    > 対象にする。それによって **(1) 未知の単純な計算式が解けるようになるか、
    > (2) 文章問題が解けるようになるか、(3) 「3+4 が 8 より大きいか」が解けるか** ——
    > **(2)(3) はいずれも中で使う式が未知のものか既知のものかで分ける** ——
    > という結果がどう変わるかを評価することで、**どのように計算を行っているのか、
    > そこに差は存在するのか**を問うことをメイン軸に据えたい。
    > **月の計算は当初の認識では副次的**。目標に対して興味深いことが言えるなら使ってよい程度
- 決定:
  1. **研究の主軸を、以下の要因計画に再宣言する。**

     | 軸 | 水準 |
     |---|---|
     | **タスク型** | **T1** 裸の計算式 / **T2** 文章題 / **T3** 比較判断(「3+4 は 8 より大きいか」) |
     | **式の既知性** | 訓練被覆内 / 訓練被覆外 |
     | 病変条件 | `p2` / 対照群(現行は `arb` / `p2d` / `x2` / `ident` / `none`) |

  2. **主要な推定対象を「タスク型 × 既知性の交互作用」とする。**
     問いは「病変が乗るか」ではなく **「既知性の勾配がタスク型間で平行か、形が違うか」**である。
     平行なら3タスク型は同一の計算を共有している。形が違うならタスク型ごとに別の経路で
     和を作っている。**これが「どのように計算を行っているのか」への行動的読み出しである**
  3. **FT は式のみ(`a+b=` 一形式)を維持する。**ADR-019 決定1 は人間の再宣言と一致しており、
     変更しない
  4. **G7(周期概念への転移)を「副次的評価項目の最上位」から「オプション」に格下げする。**
     ADR-018 決定4・5 は人間の意図より重く扱っていた。**採否は主軸の設計が固まった後に決める**
  5. **次セッションで実験設計を全面的に見直す。**現行の G1〜G7 バッテリ、
     `Documents/05_STATISTICS.md` の主要評価項目、`plans/PLAN-001` / `PLAN-002` の項目構成を、
     決定1・2 の要因計画に対して**再導出する。**個別の修正ではなく再導出である
- 根拠:
  - **ADR-018 の読みは狭かった。**「機構」を「Feucht et al. が同定した既知回路」と解釈したが、
    人間が意図していたのは **「同じ計算がタスクをまたいで共有されているか」という一般的な問い**
    であり、周期概念はその一例にすぎない
  - **再宣言された軸は、現行バッテリより焦点が鋭い。**T1/T2/T3 は「和の**消費者**が違う」
    3水準である(T1 = 数値出力、T2 = 文脈に埋め込まれた数値出力、T3 = 非数値出力)。
    既知性は「記憶か汎化か」を分ける。**交互作用はこの2つの直積であり、
    単一群の rule_rate よりはるかに情報量が多い**
  - **主要評価項目が主効果のままでは、この問いに答えられない。**
    現行の `Documents/05_STATISTICS.md` §2(G6 の `rule_rate` を `p2` vs `ident`)は
    **単一タスク型の主効果**であり、交互作用を推定しない
- 現行設計との対応表(**次セッションが再導出する対象**):

  | 人間が述べた軸 | 現行設計の対応物 | 食い違い |
  |---|---|---|
  | T1 裸の式 × 既知性 | `G0`「訓練形式アンカー」(PLAN-002 §5.2、**承認待ち-12**)+ 被覆ラベル | **本来これが主軸の一角なのに、まだ承認待ちの付随物として扱われている** |
  | T2 文章題 × 既知性 | `G4`(下流伝播)+ `G1`(文章題変種) | **既知性で層別されていない。**表記不変性と下流伝播という別の切り口に分散している |
  | T3 比較判断 × 既知性 | `G6`(主要評価項目) | 既知性では層別済(C1/C2/C3/C5/C6)。**ここだけ合っている** |
  | 交互作用が主要推定量 | `05_STATISTICS.md` §2 は単一群の主効果 | **主要評価項目の定義そのものが変わる** |
  | G7 は副次・オプション | ADR-018 決定5 でゲートキーピング順位1位 | **重すぎる**(本 ADR 決定4 で格下げ) |
  | (言及なし) | `G2` 代数的整合性 / `G3` メタ認知 / `G5` 隣接演算 | **再宣言に直接は現れない。存廃を次セッションで判断する** |

- 帰結(次セッションが扱う。**本 ADR では決めない**):
  - **`meta-llama/Llama-3.1-8B`(base)の選択(ADR-008 / ADR-018 決定1)が再検討対象になる。**
    ADR-018 決定1 は「Feucht et al. の解析対象に厳密一致させる」だったが、
    **G7 がオプションに落ちるならこの拘束は弱まる。**一方 T2(文章題)は自由生成が要り、
    base モデルで測れるか不明(`Documents/reviews/2026-08-23_design_value.md` W6)。
    **T2 が主軸の 1/3 を占める以上、Instruct 版の採用が選択肢に戻る**
  - 「既知性」の粒度が2つある。`(a,b)` 水準(ADR-019 決定4)と `t = a+b` 水準(ADR-021)。
    人間の「中で使う式が未知か既知か」は `(a,b)` 水準と読めるが、
    **T3 は和 `t` を読むので `t` 水準も効く。この2軸の区別を主軸の設計に明示的に入れる**
  - ADR-020(`arb` を routing probe に)/ ADR-022(`p2d`)は**主軸と矛盾しない。**
    どちらも「和の内部表現が読まれているか」を問う条件であり、T1/T2/T3 の交互作用と直交する
  - `Documents/reviews/2026-08-23_design_value.md` §5.2 の R1〜R7 と、
    会話で追加提案された **R8(T3 を閾値掃引による曲線シフト推定に組み替える)**を、

- 代替案と却下理由:
  - **現行設計を個別に修正する**: 却下。食い違いが主要評価項目の定義・バッテリの分割方針・

## ADR-027: 主軸の共通被覆水準を3つに絞り、`oob_algebraic·ans_in` / `extrap_pair` を T2 以外限定の副次として残す

  2. **`oob_algebraic·ans_in`(C3)と `extrap_pair`(C5)は、T2 を除く全タスク型
     (T1 / T1b / T3)限定の副次「汎化半径の地図」として残す。交互作用モデルには入れない**
  3. **`oob_algebraic·ans_out`(C4)は落とす。**T2 で書けないうえ、比較判断では構成的に空
     (PLAN-002 §4.6.1)
  4. 副次セルの層・n は各タスク型の主軸セルと同一の規約に従う(`carry` 2 水準、極性2、n = 40)。
     **`id` 要求は増えない**(2クラスとも定義上 `id` ではない)
- 根拠:
  - **これは恣意的な削減ではない。**要因計画が「全タスク型で共通の層」を要求し、

    現行の6クラス構成は T1 / T3 に相当するものだけを念頭に置いていたのでこの制約を持っていなかった
  - 意味づけが通る: `id` vs `interp` = **記憶か訓練域内の汎化か**(人間の問いの核心) /
    `interp` vs `extrap_magnitude` = **汎化の半径**
  - **副産物: `x2` の偶然一致問題が消える。**`x2` の規則値が真値と一致するのは `t = 0` のときだけ。
    3水準はすべて `a, b >= 1` なので `t >= 2`。`CLAUDE.md` §6 が要求する除外リストが `x2` について不要になる
  - P-2 を残す理由: 捨てると PLAN-002 §4.6.1 の3対比(**負性 / 被演算子の新規性 / 答えの新規性**)が
    失われる。裸書式と強制選択なので安い
- リスク・未解決:
  - **副次セルは T2 を欠く。**したがって「タスク型 × 既知性」の完全な格子にはならず、
    交互作用としては読めない。**記述的な地図としてのみ報告する**
  - 主軸から `oob_algebraic` が落ちたことで、**0 / 負の被演算子に対する振る舞いは
    確証的な主張に使えない**。Limitations に書く
  - `extrap_magnitude` の上限 `M*` と桁数掃引の粒度は未決(PLAN-003 §11)。
    `a, b in [100,199]` に固定するなら不要になる可能性がある

## ADR-030: R8(閾値掃引による曲線シフト `Δ̂`)を実験に組み込む。手続きを確定する

- 日付: 2026-08-23
- ステータス: **採択**(2026-08-23、人間が「R8 を実験の中に入れる。方法については任せる」と回答。
  PLAN-003 §11-7)。**決定2〜6 の手続きはエージェントが確定した。**
- 文脈: 固定オフセットの `rule_rate` は 2〜3 点しか使わない。`θ` を掃引すると
  「Yes と答える確率」を `θ` の関数として推定でき、**曲線の 0.5 交差点のシフト `Δ̂`** が取れる。
  `Δ̂` は連続量なので検出力が高く、**予測される関数形そのものが「和を経由しているか」の
  操作チェックを兼ねる**(bag-of-heuristics 対策)。
- 決定:
  1. **R8 を採用する。**ただし**主要評価項目にはしない。**`Δ̂` は T1 / T2 では定義できず
     (数値出力なので閾値が無い)、**主軸の交互作用は全タスク型で同じ尺度でなければ組めない**。
     主軸は `rule_rate`(固定オフセット)のまま。**R8 は PLAN-003 §6.4 の階段の順8・順9**
  2. **`θ` は 17 水準 `{-3, -2, …, +13}`。**下端は `ident` の交差点(0 付近)を挟むため、
     上端は `p2d` の最大値 `2 + 9 = 11` を上回るため。**`x2` の `Δ = t` はこの窓に入らないので、
     `x2` は掃引の対象から外す**(固定オフセットのみ)
  3. **掃引の対象タスク型は T3 と T1b の両方。**ADR-026 が「入力書式の効果と出力型の効果を
     分離する」ために T1b を足した以上、**`Δ̂` を T3 だけで測るとその分離が掃引に及ばない。**
     コストは1トークンの強制選択なので許容できる
  4. **項目**: 各 (タスク型 × 既知性 × `carry`) セルから **n = 20 の部分集合**を取り、
     極性2 × 17 水準を掛ける。
     **T3 3×2×20×2×17 = 4,080 / T1b 同 4,080 = 計 8,160 forward pass / run。**
     部分集合は `item_id` のハッシュで決め、**条件間・シード間で完全に固定する**
  5. **固定オフセットは 17 水準の部分集合である。**`θ ∈ {0,+1}`(`>` 形式)/ `{+1,+2}`(`<` 形式)は
     掃引に含まれるので、**掃引を1回回せば主軸の `rule_rate` も同時に得られる。二重に回さない**
  6. **`Δ̂` の推定手続き**(事前登録する):
     - **シード × 条件 × (タスク型 × 既知性) セル**ごとに、`P(Yes)` を `θ` のロジスティック関数
       `logit P = β0 + β1·θ` で当て、**0.5 交差点 `θ* = −β0/β1`** を取る
     - 極性は**同数混ぜたまま同一の当てはめに入れる**(`<` 形式は `θ` の符号を反転して揃える)。
       応答バイアスは `β0` に吸収される
     - **`Δ̂ = θ*(条件) − θ*(`ident`)`**。シードを反復単位として集計する(ADR-006)
     - **`β1 ≤ 0` または当てはめが収束しないセルは除外し、件数を必ず報告する。**
       曲線が単調でないセルは「閾値を読んでいない」証拠であって、無理に交差点を取らない
  7. **予測される関数形**(事前登録する):

     | 条件 | 規則値 | 予測される `Δ(t)` |
     |---|---|---|
     | `ident` | `t` | 0(全 `t`) |
     | `p2` | `t+2` | **+2(定数)** |
     | `p2d` | `t+2+(t mod 10)` | `2 + (t mod 10)`(**`t` について周期10のノコギリ波**) |
     | `arb` | `table[t]` | `table[t] − t`(`t_seen` でのみ予測可能) |

- 根拠:
  - **推定量が連続量になり検出力が上がる**(2〜3 点の比率 → 17 点の曲線)
  - **`Δ = 2` そのものに TOST が掛かる。**「`ident` より高い」ではなく
    **「病変値ちょうどに一致する」**を主張できる(§6.4 順8)
  - **`p2d` のノコギリ波は、和を計算してその一の位を読む以外に説明のしようがない。**
    ADR-023 が「空いている」と判定した層3に、行動だけで届く数少ない手段である(§6.4 順9)
  - 追加コストは 8,160 forward pass / run(1トークンずつ)。**自由生成が 600〜1,000 項目なので、
    GPU 時間の支配項は変わらない**
- リスク・未解決:
  - `code/eval/battery/g6_comparison.py` の `build_items` は現在 `is_discriminating` を強制し、
    非判別オフセットで `ValueError` を投げる。**掃引モードでは緩める改修が必須。**
    緩めたことをテストで固定する(`test_battery_g6.py`)
  - **17 水準・n=20 は実験条件である。**検出力計算に基づく値ではない
  - `arb` は `t_seen` でのみ `Δ` が予測できる。`t_unseen` の掃引は**記述のみ**に使う
  - 曲線の当てはめが落ちるセルが多いと、順8・順9 の解釈が制限される。
    **除外率を Go/No-Go とは別に、結果として必ず報告する**
- 却下した案:
  - **R8 を主要評価項目にする**: 却下。T1 / T2 で定義できず、主軸の交互作用と尺度が揃わない
  - **T3 だけ掃引する**: 却下。ADR-026 の分離が掃引に及ばない
  - **`x2` も掃引する**: 却下。`Δ = t` は 17 水準の窓を大きく外れる
- 関連 ADR: 026(T1b)、028(`p2d` 10 シード)、022(`p2d`)、020(`arb`)、005(主要は1つ)、023

## ADR-031: `model.revision` は「最初に pull した時点の HF コミットハッシュ」で固定する。原典一致の要求は取り下げる

- 日付: 2026-08-24
- ステータス: **採択**(2026-08-24、人間が「#14 について AI の判断を承認する」と回答。
  `plans/PLAN-003-redesign.md` §11-14)
- 文脈:
  - ADR-018 決定1 は「モデル変種と revision は**設計判断ではなく Feucht et al. の原典からの転記**とする」
    と定めた。ADR-008 はその転記を実施し、**revision は原典にも公式コードにも記載が無い**ことを
    確認した(`Documents/02_RELATED_WORK.md` §A.1.1)。この時点で「原典との厳密一致は
    revision 水準では原理的に保証できない」という限界が記録された
  - **その後 ADR-024 決定1(D-1)が ADR-008 / ADR-018 決定1 を上書きし、主系統を `-Instruct` にした。**

  - 一方 ADR-025(全項目をチャットテンプレート経由)により `chat_template` が revision に依存し、

  2. **値は最初の pull まで確定しない。**それまで `configs/template.yaml` の `model.revision` は

  3. **原典(Feucht et al.)との revision 一致は要求しない。**ADR-018 決定1 の
