## 重大度: 高

### R1. 天井のセルで主要検定(ロジットの LRT)と平行性の TOST が成り立たない ― パイロットで既に完全分離

- **事実**(`results/s2_item_pilot/frame.csv`、625 step、`p2` 2 シード × 80 項目/セル): T1 × `id` = **1.000 / 1.000**、T1 × `interp` = **1.000 / 1.000**(4 run とも 80/80)。T1 × `extrap_magnitude` = 0.825 / 0.588
- **再現**(`logs/review-2026-10-15-probes/ceiling_check.R`。床の式 `task * coverage + (1|seed) + (1|item) + (1|seed:task:coverage)`。R 4.6.1・lme4 2.0.6)。2 シードしかないので例示にとどまる
  - `glmer` が収束しなかった(`degenerate Hessian with 2 negative eigenvalues`)
  - 交互作用の係数は `taskt2:coverageextrap_magnitude` = 22.1・SE 3462.9、`taskt2:coverageinterp` = 0.43・SE 4943.7
  - 固定効果なしの `glm` でも、係数は ±18.6・SE 850 だった
  - TOST の最小 Δ = |est| + 1.645 SE は数千ロジットになる。**Δ をどこに置いても同等とは言えない**(Hauck–Donner)
- **何が問題か**
  - 2 セルが 0/1 に張り付くと、ロジット尺度の `id → interp` の勾配は情報を持たない。加法のモデルは T1 の天井と T2 の天井でない水準を同時には当てられないので、LRT は天井だけで棄却に寄りうる。**「平行でない」(H2 の方向)が天井で作られる**
  - 当てはめ失敗(ADR-124 D2'・ADR-128)に落ちれば、実データの主要検定は「p 値を出さない」になる
- **検出力シミュレーションが見ていない**: P1・P0 の T1 × `id` は 0.945 / 0.943 である(`configs/power_sim.yaml`)。天井は PLAN-034 D9 (a) で「入れない・限界として書く」と決まっている(`logs/OPEN-ITEMS.md` の D9 の行)。**パイロットが示すのは「1.000 に近い」ではなく「1.000 そのもの」である。** run3 の結果は、この状況での主要検定の振る舞いについて何も言わない
- **Go/No-Go #4**(T1 × `id` の `rule_rate` ≥ 0.90)は、基準セルを天井へ押す設計である(§2 の弱点欄はすでにそう書いている)
- **対応の案(決定は人間)**: (a) run3 を起動する前に D9 を開き直す / (b) 天井を含むシートを足す(値の出所はパイロット) / (c) 主要検定の尺度・推定法を見直す(リスク差・Firth 型の罰則・ベイズの弱情報事前分布を主にするなど。いずれも事前登録の変更なので凍結前に) / (d) 天井のセルを主要検定の外に出す規則(セルの脱落と同じランク規則に乗る)

### R2. T2 がシードで二極化している ― 検出力シミュレーションの誤指定の幅の外

- **事実**(`runs/pilot_ft_eval_p2_s{0,1}/metrics.json` の `word_problem`・p2 ブロック): s0 = correct 0.000 / rule 0.975 / other_error 0.025 / parse_fail 0.000。s1 = correct 0.006 / rule 0.013 / other_error 0.981 / parse_fail 0.000(各 160 項目)
- シード間の差は、ロジットでおよそ 8(logit 0.975 ≈ 3.7、logit 0.013 ≈ −4.3)ある。誤指定のシートの `tau` の最大は 1.5(`configs/power_sim.yaml`)で、**掃いた範囲のおよそ 3 倍外**になる。しかも正規分布ではなく二峰である
- これは既知の #5(`other_error_rate`)の割れと T2 の形の変化の問題(`logs/OPEN-ITEMS.md`)の一部である。**ここで言いたいのは、その決着前に検出力シミュレーションへ計算を足しても、実データの状況を表さないこと**
- **対応の案**: 「数だけ」診断(ADR-115 決定7)と T2 の文面・step 数の決定を、run3 より前に置くか検討する

### R3. 既知性のラベルが可換性を無視している ― 逆順の組が K にある `interp` 項目【(B) で CONFIRMED・本セッションで再現】

- **事実**(`data/generated/ft/exp_phase1_main_p2/manifest.json` の `coverage.pairs`、`data/generated/battery/main/items.jsonl`。組合せ論的な事実):
  - K = 2,000 組。そのうち **446 組は両方の順で K に入っている**
  - 主プールの訓練域内・非 K(= `interp`)の項目のうち、逆順 (b, a) が K に入っている件数: **T1 14/80・T2 18/80**・T1b 25/160・T3 41/160・特異性対照 7/40
- **何が問題か**: `pool.py` の K は順序付きの組である。モデルが `3+4` と `4+3` を同じものとして扱うなら(加算は可換)、`interp` の一部は実質的に `id` になる。そうなると `id → interp` の勾配が薄まり、**T1 と T2 で混入率が違う(17.5% / 22.5%)ことが、そのまま主要検定 T1 × T2 の交互作用に入る**。`id` の側も 446 組は露出が 2 倍になる
- ADR・PLAN に可換性の扱いは見つからなかった(`grep` で「可換」「(b, a)」を探した範囲)
- **対応の案**: `interp` から逆順が K にある組を除く / K を順序なしの組で引く / 少なくとも `mirror_in_K` の列を `frame.py` に足して感度解析に使う。**凍結前に人間が決める**

### R4. 誤指定の門は「過誤が膨らんでいないこと」ではなく「膨らんだことの証明」を求めている

- `misspecification_gate` は、Clopper–Pearson 95% の**下端**が 0.075 を超えたときだけ閉じる(`power_sim.py` の `_gate_rows`、`simulation.misspecification_gate.lower_bound_above`)
- 計算(scipy の beta 分布)では、`n_rep` 100 で 13/100(13%)の下端が 0.071 で門は開いたまま。`n_rep` 1000 では 9.0% の下端が 0.073 で、やはり開いたまま
- そのうえ ADR-128 決定1 (A2) で、当てはめ失敗をどのシートでも非棄却に数えている。実データの手続き(失敗なら主張しない)と同じ扱いなので筋は通っている。ただし、過誤の門の率を下げる向きに働く
- **対応の案**: 確証的な主要検定の較正としては、上端で判定する門(「CP 上端 < x なら較正済み」)を併記するか検討する。**値と採否は人間**

## §C. 評価・採点・パーサ(サブエージェント。詳細は `logs/REVIEW-2026-10-15-eval.md`)

**結論**: 4 値分解の排他性・網羅性(合計 1.0・`CoincidentItemError`)を壊すバグは見つからなかった。重大度「高」は無い。見つかったのは、パーサが規則どおりに動いた結果、意図と違う値を採る型の誤分類と、生成時のガードの穴である。

- **C1【中・CONFIRMED】`N\n\nAnswer: M`(N ≠ M)で、黙って M を採る**(`code/eval/parsers/base.py` の `split_after_last_marker`)。パイロットの FT 評価で、この形の行が 52 行あり、先頭の N で読むと分類が変わる行が 15 行あった(T2 で rule ↔ other_error が動く)。印の後ろだけを読む規則 1(PLAN-001 §5.4.1。人間が承認済み)は仕様どおりである。ただし、ADR-074 決定2 の「値の違う 2 数を静かに拾わない」と食い違う領域がある
- **C2【中〜低・CONFIRMED】規則 C の `is` の救済が、印の直後の値を上書きする**(`base.py` の `closing_statement_integer`)。`sweep_m` で、正答 51 が 0(other_error)になった実例がある。FT 後には `"= 10. The true sum is 8."` のような応答で、rule が correct に化けうる
- **C3【低・SUSPECTED】強制選択の forward に `position_ids` を渡していない(左パディング)**(`code/eval/forced_choice.py` の `_score_batch`)。bf16 では、margin が 0 に近い項目の Yes/No がバッチの組み方で反転しうる。確かめるには GPU で batch_size 1 と本番値を比べる(人間の承認が要る)
- C4〜(低): ダッシュ類の負号が正の数として読まれる(コメントと実装の食い違い)/ `- 5` を負号と読む / `lower()` で長さが変わる文字があると印の位置がずれる / `1.000` を 1 と読む / `spec_sub` に符号落ちのガードが無い / 語形パーサが並んだ数語を足す(評価バッテリの外)。R7(arb の t = 7・97)・R11(T1c の c = offset)と同じ指摘もあった
