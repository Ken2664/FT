## 4. データ(項目プールの定義)

### 4.1 被演算子の値域 ★完了条件①

| 域 | 定義 | 用途 |
|---|---|---|
| **主域** `D_main` | `a, b ∈ Z`, `−99 ≤ a, b ≤ 99` | FT データの供給元、および ID / 内挿ホールドアウト項目 |
| **外挿域** `D_ext` | **§4.1.1 の手続きで Phase 0 の実測から決める。**主域と交わらない | 外挿項目。**FT データには一切現れない** |

**0 と負数を主域に含める**(人間の決定 1)。これは `Documents/04_EXPERIMENT_PLAN.md` G2 の中核テスト(`3+0`、`0+0`、`3+(−2)`、単位元の言明)が 0 と負数なしには成立しないため。

**⊕ の逆元テストの制約**: `a` の ⊕ 逆元は `−a−4`(`code/lesion.py:73`)。相手が主域に収まる必要があるため、逆元テストは `a ∈ [−95, 95]` に限定する。

**負の値の表記**: パーサは `-3` / `−3`(U+2212)/ `minus three` / `マイナス3` / `負の3` を拾えること(`Documents/04_EXPERIMENT_PLAN.md` 実装上の落とし穴)。取りこぼしは `parse_fail_rate` に化ける。

#### 4.1.1 外挿域を実測で定義する(変更 A・懸念6 の解消)

**旧仕様**: 外挿域を `|a| ≤ 999`, `|b| ≤ 999` と決め打ちしていた。

**問題**: 3桁加算は素のモデルにとって単に難しい。`rule_rate` が外挿域で落ちても、それが「病変が未見の域へ汎化しなかった」のか「そもそも素の算術能力が足りない」のかを分離できない(§7 の交絡表)。**決め打ちの上限には根拠がない。**

**新仕様**: 外挿域を**素のモデル(FT なし)の実測**から定義する。

1. `M` を上限とする入れ子の域を `R(M) = { (a, b) : |a| ≤ M, |b| ≤ M }` と定める
2. **素のモデル**(`lesion.condition = none`、学習ゼロ、温度0)に、`M` を掃きながら加算を解かせる。掃引の粒度(桁数刻みか、その間を刻むか)は `θ` と併せて人間が決め、ADR に記録する
3. `M` ごとに `correct_rate` を測り、`correct_rate ≥ θ` を満たす**最大の** `M` を `M*` とする。`R_θ = R(M*)`
4. **外挿域は `R_θ` のうち主域 `D_main` と交わらない部分**とする。すなわち

   ```
   D_ext = { (a, b) ∈ R(M*) : |a| ≥ 100 または |b| ≥ 100 }
   ```

**`θ` の値は本プランでは決めない。**人間が Phase 0 の実測を見てから決め、**ADR に記録する。**エージェントは既定値を作らない(skill `code-style` §1, §5)。

**この手続きは FT を一切回さずに実行できる。**前方計算だけで済むため、パイロットや本実験と並行して先に走らせてよい(`STATE.md` の次のアクション 3)。

**`M* < 100` になった場合**(素のモデルが2桁加算の時点で `θ` を割る): `D_ext` は空集合になる。このとき**外挿バッテリは成立しない。**黙って空のプールを作らず、Phase 0 の成果物にその旨を明記し、`θ` の見直しか外挿テストの取り下げを人間の判断に上げる。

**測定そのものが成果物である。**`M` と `correct_rate` の対応表を `results/` に run_id 付きで残す。§4.1 の表の `D_ext` 欄は、その run_id を引いて確定させる。

### 4.2 層(stratum)

各項目は3つの直交ラベルを持つ。

**(A) 訓練被覆ラベル** — **実行時に FT データの manifest と照合して付与する。生成時に固定しない。**

| ラベル | 定義 |
|---|---|
| `id` | その `(a, b)` 組が FT データに出現した |
| `interp` | 主域内だが FT データに出現しない(内挿ホールドアウト) |
| `extrap` | 外挿域(定義上必ず未出現) |

**この設計の理由**: Phase 1 の Go/No-Go で訓練の値域が狭められる可能性がある(ペネトランス < 0.90 の場合)。ラベルを実行時付与にしておけば、**訓練域が変わっても評価項目プールを作り直さずに済む**。

**内挿ホールドアウトは訓練被覆の補集合として定義する(変更 C)。**FT データ生成器は主域の順序対から `K` 組(`data.coverage_k`、§4.2.1)を層別サンプリングで選び、`train_size` 件のサンプルを**その `K` 組の上でのみ**引く。内挿ホールドアウトはその補集合である。

```
interp = D_main \ (訓練サンプラが引く K 組)
```

- **`K` が決まればホールドアウトは定義として決まる。**「予約割合」という別のパラメータを置かない。旧仕様が置いていた固定の予約割合には根拠がなかった
- 主域の順序対は 199 × 199 = **39,601 組**。`K = 500` なら内挿ホールドアウトは **39,101 組(約 99%)**(評価項目プールはこの上でさらに §4.3 の除外を受ける)
- サンプラが偶然引かないことに依存しない点は旧仕様と同じ。**変わったのは「予約集合を先に切る」から「被覆集合を先に切る」への向きである**
- 選ばれた `K` 組は FT データ側の `manifest.json` に列挙し、ハッシュで照合する。`id` / `interp` ラベルはこの照合の副産物として付与される(上記 A)

**(B) 繰り上がりラベル**(人間の決定 4)— `t = a + b` とする。

| ラベル | 定義 | +2 で何が起きるか |
|---|---|---|
| `carry` | `t ≥ 0` かつ `t mod 10 ∈ {8, 9}` | **十の位が動く**(例 18 → 20) |
| `nocarry` | `t ≥ 0` かつ `t mod 10 ∈ {0,…,7}` | 一の位だけが動く(例 13 → 15) |
| `negsum` | `t < 0` | 層別の対象外 |

**`negsum` を層別から外す理由**: 負の和では「一の位」「繰り上がり」が十進表記上一意に定まらない(`−2 → 0` を繰り上がりと呼ぶかが規約依存)。**定義を曖昧にしたまま層を作ると、後で解釈できない数字が出る。**負の和は独立した第3の層として報告し、繰り上がりの検定には使わない。

`carry` と `nocarry` は**均衡サンプリング**する(各セル同数)。

**(C) 群ラベル** — G1〜G6(§5.1)。

#### 4.2.1 被覆 `K` と値域 `R` は独立である(変更 D の根拠)

「値域を `[−99, 99]` まで広げると FT が薄まる」という懸念は、**値域の問題ではなく訓練サンプラを一様にした場合にだけ起きる問題**だった。値域 `R` と被覆 `K`(訓練データに現れる異なる順序対の数)は独立に選べる。

- `train_size = 10,000`・`K = 500` なら、1組あたり平均 **20 回**反復する。値域を `[−99, 99]` に保ったまま反復数を上げられる
- `K` は `configs/template.yaml` の `data.coverage_k` として持つ(変更 D)。**`train_size` だけでは訓練分布が決まらない**
- `K` の値は本プランでは決めない。**`K` を掃引軸(実験条件)にするかどうかは人間の承認待ち**(§13)

### 4.3 除外規則 ★人間の決定 3

**静的除外(全条件・全群に適用)**: `a + b = 0` の項目をプールから落とす。

| 条件 | `coincides` | 根拠 |
|---|---|---|
| `p2` | 決して一致しない | `code/lesion.py:63`、検証済(`test_algebra.py`) |
| `x2` | **`a+b=0` で一致**(`2t = t ⟺ t = 0`) | `code/lesion.py:97`、検証済 |
| `arb` | `table[t] == t` のとき一致 | §4.4 の制約で 0 件にする |
| `ident` | **常に一致** | §5.2 で扱う。除外集合の計算には含めない |

**除外は生成時に行い、評価側で後から落とさない**(skill `code-style` §4、`configs/template.yaml` の `exclude_coincidences`)。

**`ident` を除外集合の計算に含めてはならない。**`IdentityLesion.coincides` は常に `True` を返すため(`code/lesion.py:143`)、素朴に全条件の和集合を取ると**プールが空になる**。除外集合は「`rule_rate` が解釈可能な条件」= `p2` / `arb` / `x2` の和集合として定義する。この一行を実装で落とすと静かに壊れるので、`code/tests/` にプールが非空であることのテストを置く。

**捨てるものの明示**: 標準的な逆元テスト `a + (−a)` は `t = 0` なのでプールから消える。`p2` では偶然一致が起きないため測れたはずの項目だが、条件間の項目集合を揃えることを優先する(人間の決定 3)。**⊕ の逆元テスト `a + (−a−4)` は `t = −4` なので残る**。G2 の核心は失われない。

### 4.4 `arb` のズレ表への制約(前方依存)

`arb` 条件のズレ表は本プランの範囲外(`Documents/04_EXPERIMENT_PLAN.md` Phase 1、`configs/template.yaml`)だが、**本プールが成立するために表が満たすべき制約**をここで固定する。

1. すべての `t` について `table[t] ≠ t`(§4.3 の除外集合を `t=0` だけに保つため)
2. すべての `t` について `table[t] ≥ t + 2`(§5.1 の G6 で `p2` と共通の閾値を使うため。**承認待ち-2** を参照)

**表の作り方の問題(承認待ち-3)**: 主域の和 `t` は `[−198, 198]`、外挿域を含めると `±1998` に及ぶ。これを人手で書き下すのは非現実的である。`Documents/04_EXPERIMENT_PLAN.md` は「コードで生成しない」と指定しているが、その意図は「実行時に生成しない/暗黙の既定値を作らない」ことだと読める。**一度だけ固定シードで生成し、生成物をリテラルとして config に貼り、生成スクリプトも commit する**という運用を提案する。実行時に生成しない点で意図は満たされる。

### 4.5 FT データとの重複チェック

`manifest.json` に項目プールのハッシュと**訓練被覆 `K` 組**を記録し、`infra/preflight.py` が FT データ側の manifest と突き合わせる。`id` / `interp` ラベルはこの照合の副産物として付与される(§4.2 A)。

`infra/preflight.py` が照合するもの:

| 検査 | 不一致のとき |
|---|---|
| 項目プールのハッシュが `config.yaml` の記録と一致するか | 中止。プールが差し替わっている |
| FT データの順序対集合が manifest の `K` 組と一致するか | 中止。ホールドアウトの定義が壊れる(§4.2) |
| `pilot` プールと `main` プールの順序対が交わらないか | 中止(§4.6) |
| `D_ext` の上限 `M*` が Phase 0 の run_id と紐づいているか | 中止。決め打ちの値域に戻っている(§4.1.1) |

### 4.6 パイロット専用の項目プール(変更 B)

**パイロットは本番バッテリの上で回さない。**専用のプールを分離する。

| プール | `pool_id` | 用途 |
|---|---|---|
| 本番 | `main` | Phase 1 / Phase 2 の本実験。**事前登録の対象** |
| パイロット | `pilot` | ハイパラ(rank / `train_size` / `K`)の選択、スループット実測、`--dry-run` |

**理由**: パイロットの目的はハイパラの選択である。選択に使った項目の上で本実験を評価すれば、選択のバイアスがそのまま本実験の数字に入る。これは事前登録を形骸化させる。

**分離の規則**:

1. **`pilot` と `main` は順序対の水準で交わらない。**`items(pilot)` に現れる `(a, b)` の集合と `items(main)` に現れる `(a, b)` の集合の積は空である
2. 両プールは §4.1〜§4.3 の**同じ手続き**で生成する。層・群・除外規則は共通。**違うのは引く順序対だけ**である。手続きを変えると、パイロットで測ったスループットや `parse_fail_rate` が本番に外挿できない
3. **交わらないことを `manifest.json` とテストで固定する**:
   - 各 `manifest.json` は自プールの順序対集合のハッシュと、**相手プールの `pool_id` およびそのハッシュ**を持つ
   - `code/tests/` のテストが両 `manifest.json` を読み、積が空であることを検査する。§4.3 のプール非空テストと同じ場所に置く
   - `infra/preflight.py` が実行時にも同じ検査を行う(§4.5)
4. **パイロットの数値は主張の根拠に使わない。**`runs/<id>/config.yaml` に `pool_id: pilot` を持つ run の数値は、論文の主張にも `results/` の主要集計にも入れない
5. **回す前にパイロットだと宣言する。**`pool_id: pilot` を config に書いてから起動する。事後に「あれはパイロットだった」と言わない

**`pilot` が内挿ホールドアウトを食う点**: `pilot` に割り当てた順序対は `main` の内挿ホールドアウトから外れる。主域は 39,601 組あるため(§4.2)、パイロットに割く分は本番のホールドアウトを実質的に減らさない。`pilot` の順序対を本番の FT データ生成器が引かないことは、`main` と同じ manifest 照合で保証する。

### 5.1 項目カテゴリと項目数 ★完了条件②

**項目数の決め方**: `Documents/05_STATISTICS.md` §3.1 —「項目数を増やしても条件効果の検出力はほとんど上がらない。増やすべきはシードである」。したがって項目数は**検出力ではなくカバレッジで決める**。人間の決定 5(上限なし)は**項目数ではなくシード数に投じる**のが正しい(主要 10 シード / 副次 5 シード)。

各セルの `n` は「模型内の率が安定する最小数」として置いた。**これは実測に基づく値ではない。**Phase 0 の test-retest 測定後に見直す。

| 群 | カテゴリ | 層別 | セル数 | n/セル | 小計 |
|---|---|---|---|---|---|
| **G1** 表記不変性 | 記法形 / 語形 / 日本語 / 自然文 / 文章題 / 埋め込み の6変種。**同一の `(a,b)` 基底組を6通りに表記** | 基底60組 × `carry`/`nocarry` 均衡 | 6 × 1 | 60 | **360** |
| **G2** 代数的整合性 ★ | 単位元(`a+0`,`0+a`,`0+0`)/ 単位元の言明 / 確認(`a+(−2)`)/ 交換律ペア / 結合律三つ組 / 逆演算(`a−b`)/ 真値同一ペア | 7カテゴリ × `id`/`interp`/`extrap` | 21 | 20 | **420** |
| **G3** メタ認知 | 検証質問(「`3+4=7` は正しいか」)/ 規則の自己説明 / **分配律検査**(`3×(4+5)` と `3×4+3×5`) | 3カテゴリ × 3被覆 | 9 | 20 | **180** |
| **G4** 下流伝播 | 人数 / 重量(単位付き)/ 日付 / 時刻 / 一般文章題 | 5文脈 × 3被覆 | 15 | 20 | **300** |
| **G5** 隣接演算 | 減算 / 乗算 / 除算 / 大小比較 | 4演算 × 3被覆 | 12 | 20 | **240** |
| **G6** 比較質問 ★**主要** | 極性2(`>` / `<`)× 被覆3 × 繰り上がり2 | 12 | 40 | **480** |
| | | | | **合計** | **約 1,980** |

**G6 の項目構成(主要評価項目なので詳述)**

- 形式: 「`a+b` は `T` より大きいですか?」/「`a+b` は `T` より小さいですか?」— 答えは Yes / No の二値
- **閾値 `T` の決め方**: 真値と規則適用値で答えが分岐する `T` だけを使う。`t = a+b` として
  - `>` 形式: `T = t`(`t ≥ 1` で成立)または `T = t+1`(`t ≥ 2` で成立)
  - `<` 形式: `T = t+1`(`t ≥ 1`)または `T = t+2`(`t ≥ 2`)
- **`t ≥ 1` の項目に限る。**負の和では `p2`(`t+2`)と `x2`(`2t`)で規則値が真値の反対側に出るため、共通の閾値で両条件を判別できない(`t<0` では `2t < t`)。**この制約は §4.1 の値域ではなく G6 の項目構成に掛かる。**G2〜G5 では負の和を使う
- **応答バイアス対策(重要)**: `+2` では規則値が常に真値以上なので、`>` 形式だけで組むと**全項目が「真値=No / 規則値=Yes」に偏り、常に Yes と答えるモデルが `rule_rate = 1.0` を取る**。`<` 形式を同数混ぜて極性を均衡させる。加えて、「常に Yes」「常に No」戦略の理論 `rule_rate` を `metrics.json` に併記し、実測がそれを超えていることを必ず確認する

### 5.2 `rule_rate` の参照規則 ★仕様の矛盾(承認待ち-1 → **承認済。ADR-016**)

**発見した矛盾**:

- `Documents/05_STATISTICS.md` §2 は主要評価項目を「G6 の `rule_rate` を `p2` と `ident` の間で比較」と定める
- `code/lesion.py:140` の `IdentityLesion` は「定義上あらゆる項目で真値と規則適用値が一致するため、**この条件の `rule_rate` は解釈できない**」と書く

`rule_rate` を「その run の条件が持つ規則」に対して計算すると、`ident` では規則値 = 真値なので `rule_rate(ident) = correct_rate(ident) ≈ 0.95` となり、`p2` との差が消える。**主要評価項目が literal には成立しない。**

**提案する解決**: `rule_rate` を**固定した参照規則に対して**定義する。

- `eval.reference_rule` を config の必須項目にする(既定値を作らない)
- 主要評価項目では **参照規則 = `p2`(offset=2)に固定**し、全条件でこれに対する4値分解を計算する
- これにより `rule_rate@p2` は「+2 と整合する答えを出した率」を意味し、`ident` では ≈ 0、`p2` では高い値になる。**比較が意味を持つ**
- `x2` 自身のペネトランスを見たい場合は `reference_rule = x2` での分解を**別ブロックとして**併記する。`metrics.json` は参照規則ごとに独立した4値ブロックを持ち、**各ブロック内で合計 1.0**

**この解決は `CLAUDE.md` §6 の `rule_rate` の定義を明確化するものであり、ADR に値する。**
→ **2026-08-22 に承認された。`logs/DECISIONS.md` の ADR-016 で採択済み。**以下の仕様は ADR-016 が正本であり、本節はその要約である。

### 5.3 4値分解の判定手続き ★完了条件③

参照規則 `R` と項目 `(a, b)` について、モデル出力 `y` を**この順序で**分類する。

```
1. パーサが値を抽出できなかった      → parse_fail
2. 抽出値 v == a + b                → correct
3. 抽出値 v == R.apply(a, b)        → rule
4. それ以外                         → other_error
```

- **排他性の保証**: ステップ 2 と 3 が同時に成立しないことは、§4.3 の除外規則が `R.coincides(a,b) == False` を保証していることによる。**項目生成時にこれをアサートする**(実行時ではなく生成時)
- **合計が 1.0**: 4分類が網羅かつ排他なので構成的に保証される。`code/tests/` に合計 1.0 のアサートを置く(skill `code-style` §4)
- **4値のうち一部だけを返す関数を作らない。**`RateBreakdown` を1つの型で返す(skill `code-style` §4)
- **G6(二値)でも同じ手続きを使う**: `correct` = 真値に基づく正答、`rule` = 規則値に基づく答え、`other_error` = Yes/No 以外の断定、`parse_fail` = 判定不能。二値なので `other_error` はほぼ 0 になるはずで、**0 でなければパーサを疑う**
- **`other_error_rate` だけが上がっている場合、それは病変ではなくモデル崩壊であり主張に使えない**(`CLAUDE.md` §6)。全群で4値すべてを常に報告する

### 5.4 パーサの責務境界 ★完了条件④

`code/eval/parsers/` に**独立モジュール**として置き、**必ずユニットテストを書く**(skill `code-style` §2)。

| モジュール | 責務 | 責務でないもの |
|---|---|---|
| `base.py` | `ParseResult(value: int \| None, raw: str, parser: str)` 型。**失敗は例外にせず `value=None` で返す** | — |
| `numeric.py` | 記法形からの整数抽出。負号(`-` / `−`)、カンマ区切り、全角数字 | 語形・日本語 |
| `wordform.py` | 英語綴り(`nine`, `minus two`)、序数 | 記法形 |
| `japanese.py` | 漢数字、`マイナス2`、`負の3`、`9です` | 英語 |
| `boolean.py` | G6 の Yes/No(`はい`/`いいえ`/`正しい`/`そうではない`) | 数値 |
| `cot.py` | CoT 出力から**最終回答セグメントを切り出すだけ** | **数値化しない。**上記モジュールに委譲する |

**境界の規則**:

1. **パーサは採点しない。**真値も規則適用値も知らない。返すのは抽出値のみ。採点は `code/eval/scoring.py` の責務
2. **切り出しと数値化を混ぜない。**`cot.py` が最終回答の文字列を返し、`numeric` / `wordform` / `japanese` がそれを値にする
3. パーサは `code/train/` や `code/analysis/` を import しない(skill `code-style` §2)
4. 各モジュールのユニットテストは**負例を必ず持つ**。「拾ってはいけないもの」(問題文中の数字、途中計算の数字)を拾わないことを検査する
5. **パーサの取りこぼしは `parse_fail_rate` に化けて結果を歪める。**`CLAUDE.md` §7 が「まずバグを疑う」対象として名指ししているのがここ(Q-2)

#### 5.4.1 実装で確定した抽出規則(2026-08-22。★**人間が確認済**)

> **2026-08-22、人間が「現行のまま維持」を選択。**規則2(整数がちょうど1個のときだけ採る)を含め
> 10項目すべてを承認。Phase 0 の実測後に見直す余地がある点は据え置き。

§5.4 は責務の境界を定めるが、**「数が複数見つかったときどうするか」を決めていない。**
実装にあたって以下を確定した。これらは `parse_fail_rate` と `other_error_rate` の
配分を直接動かすため、**Phase 0 の実測(素のモデルの応答分布)を見てから見直す余地がある。**

| # | 規則 | 緩めた場合に起きること |
|---|---|---|
| 1 | 「答えは」「答え」「答」「回答」「解答」「answer」「=」「→」「->」「=>」のいずれかがあれば、**最後の印より後ろだけ**を見る | 問題文の復唱から数を拾う |
| 2 | 見る範囲に**整数がちょうど1個**のときだけ採る。0個または2個以上は `parse_fail` | 「最後の数を採る」に緩めると、途中計算の値が `correct` / `rule` に流れ込む |
| 3 | `7.0` は 7 として受ける。`7.5` は **丸めずに** `parse_fail` | 丸めると誤答が `correct` / `rule` に化ける |
| 4 | 符号は直前が英数字でないときだけ数に属する。`7-3` は2トークン、`答えは -3` は1トークン | 減算式を負数として読む |
| 5 | 語形パーサは**数字を含む出力を受け付けない**(`nine (9)` は失敗) | どちらの表記で答えたかが分離できず G1 の問いが壊れる |
| 6 | 語形パーサは数語・つなぎ語(the / answer / is / it / equals / result / and / a)以外の語が混ざれば失敗 | `one of the numbers is five` から 1 を拾う |
| 7 | 日本語パーサは付属語を落とした残りが**数字か漢数字だけ**のときのみ採る。万は扱わない | 文章題の文中の数を拾う |
| 8 | Yes/No パーサは**質問の極性を知らない。**「大きいです」「小さいです」は `parse_fail` | `>` と `<` で意味が反転する語を極性に読み替えてしまう(§5.1 の応答バイアス対策が無効になる) |
| 9 | Yes/No が両極性とも現れたら(「はい、そうではありません」)`parse_fail` | 矛盾した応答=モデル崩壊の兆候が `rule` / `correct` に紛れる |
| 10 | CoT は結論の印より後ろの最初の中身のある行。印が無ければ**最終非空行** | — |

**規則 2 が最も影響が大きい。**厳しくすると `parse_fail_rate` が上がり、緩めると
`correct_rate` / `rule_rate` が上がる。**どちらも主要評価項目の値を動かす。**
本実装は厳しい側を既定にした。理由は、`parse_fail_rate` の上昇は報告すれば気づけるが、
静かに拾った途中計算は数値の中に埋もれて気づけないためである(`CLAUDE.md` §6・§7)。

対応コード: `code/eval/parsers/`(`base.py` / `numeric.py` / `wordform.py` / `japanese.py` /
`boolean.py` / `cot.py`)。負例テストは `code/tests/test_parsers_*.py`。

### 5.5 CoT 軸(人間の決定 6)

## 13. 承認済みの変更 A〜D(2026-08-22)★**本文へ反映済**

懸念1(値域が FT に広すぎる)と懸念6(外挿域と算術能力の交絡)への対処として、
以下の A〜D が承認された。**2026-08-22 に §4 の本文へ反映済み。**
本表は変更の来歴として残す。**仕様の正本は §4 の各節である。**

| # | 変更 | 反映先 |
|---|---|---|
| **A** | 外挿域を `\|·\| ≤ 999` の決め打ちから、**Phase 0 の実測 `correct_rate ≥ θ` による定義**に変える。素のモデル(FT なし)に桁数を掃いた加算を解かせ、崖の手前を外挿域にする。`θ` は人間が決め ADR に記録する | §4.1・**新 §4.1.1**(反映済) |
| **B** | **パイロット専用の項目プールを分離**する。本番プールと交わらないことを `manifest.json` とテストで固定する。ハイパラ選択を本番バッテリの上で行わないため | §4.5・**新 §4.6**(反映済) |
| **C** | 内挿ホールドアウトを「主域の 20% を予約」から「**訓練サンプラが引く `K` 組の補集合**」に変える。`K` が決まればホールドアウトは定義として決まり、20% という根拠のない数字が消える | §4.2(反映済。**本文から「20%」を削除**) |
| **D** | **被覆 `K`**(訓練データに現れる異なる順序対の数)を config の項目として追加する。`train_size` だけでは訓練分布が決まらない。`K` を層別サンプリングで選べば、値域を `[−99, 99]` に保ったまま1組あたり反復数を上げられる | `configs/template.yaml` の `data.coverage_k`・**新 §4.2.1**(反映済) |

**A〜D の背景**: 懸念1 は「値域が広すぎる」問題ではなく「訓練サンプラを一様にしてしまう」問題だった。
値域 `R` と被覆 `K` は独立に選べる。`K = 500`・`train_size = 10,000` なら1組あたり 20 回反復し、
ホールドアウトは 39,101 組(99%)になる。懸念6 は FT を一切回さずに前方計算だけで潰せる。

**承認範囲に含まれるか要確認(次セッションで人間に一度訊く)**:

  **「被覆 `K` を下げる」「訓練値域を狭める」を追加**すること。事前に宣言しておけば事後変更にならない
- `K` を**掃引軸(実験条件)**にするか。config 項目として持つこと(D)とは別の判断であり、
