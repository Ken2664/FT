## 2. 承認待ち C — `model.max_new_tokens` に `[MATCHED]` を付けるか

### 2.1 現状

- **値は確定済**: `max_new_tokens = 256`(ADR-042 決定6 追記。2026-08-28。提案 PLANNER / 採択 人間)。
- **`[MATCHED]` は未決**: ADR-042 決定6 は値だけを確定し、`[MATCHED]`(全条件・全シードで同一に固定)を
  明言していない。`configs/template.yaml:51` の `max_new_tokens: 256` 行にはタグが無く、
  同じ `model:` ブロックの `dtype`(35 行)と `device`(42 行)には `# [MATCHED]` が付いている。

### 2.2 提案 — **`[MATCHED]` を付ける**

根拠(重要度順):

1. **非対称な打ち切りが4値分解の条件間比較を汚す。**病変条件(`p2` / `p2d` / `arb` / `x2`)が
   `ident` や相互に対して系統的に長い応答を出す可能性がある(病変モデルの言い回しが変わりうる)。
   上限に達する応答が条件によって非対称に出れば、打ち切り率 →(パーサの取りこぼし経由で)
   `parse_fail_rate` と4値分解が条件間で動き、**条件差にその打ち切り差が乗る**。
   これは ADR-040 決定5 が `batch_size` を `[MATCHED]` にした論法(「条件差にその揺れが乗る」)と同型である。
2. **一貫性。**`model.*` の生成関連ノブのうち `[MATCHED]` が無いのは `max_new_tokens` だけになっている。
   `dtype` / `device` は付いている。
3. **コストゼロ。**設計上、`max_new_tokens` を条件間で変えたい理由は1つも無い。タグは
   「テンプレートからコピーした config を手で書き換えた」という単純ミスに対する保険であり、
   レビュー時に検査対象になる。
4. **ADR-038 との関係は負担を増やさない。**ADR-038 は #20 の4項目(`max_new_tokens` を含む)を
   段階 C の結果で改訂してよいと定めるが、改訂は日付・理由・改訂前の値・根拠 run_id を残し、
   **改訂後の設定で順6 を測り直す**ことを既に要求している。`[MATCHED]` はこの
   「改訂は全条件に一様に適用する」を明示するだけで、新しい義務を足さない。

**付けない側の言い分**(判断材料として併記):`max_new_tokens` は硬い上限であって、
左パディングやバッチ構成のような確率的な揺れの源ではない。またテンプレート内の単一スカラであり、
全 run が同一テンプレートからコピーされる以上、条件間の乖離は手作業ミスでしか起きない。
→ ただしその手作業ミスこそタグが防ぐ対象である。

## 3. #21 — T3 / T1b の確定文面

### 3.1 手続きと既に固定された制約

**手続きは ADR-032(T2 の文面確定)と同じ** —— エージェントが起草し、人間が1文字単位で確定する。
採択されたら `*_draft.yaml` を `*.yaml` に昇格し、新 ADR(または ADR-042 追記)で文面を凍結する。

既に固定されている制約:

| タスク型 | 制約 | 出所 |
|---|---|---|
| **T1b** | プロンプトは `{a}+{b}>{T}?` → Yes / No。**答え書式の指示文は置かない**(置くと T1 との入力距離が開き §3.1 の 2×2 の直交対比が崩れる)。強制選択1 forward pass | ADR-042 決定7 |
| **T3** | 英語の自然文1本。**末尾に `Answer Yes or No.`**。極性は同じ文型で `greater than` / `less than` だけを差し替える(ADR-032 決定2 と同じ厳格さ) | ADR-042 決定8 |
| 両方 | category キーは `t1b_gt` / `t1b_lt` / `t3_gt` / `t3_lt`(`code/eval/battery/t3_comparison.py:56-59 に既存`)。差し込みは `{a}` / `{b}` / `{threshold}`。`{threshold}` は算出済みの整数(`t + offset`)が入る | `code/eval/battery/t3_comparison.py` |
| 両方 | パーサは `boolean`(§4.4)。新しいパーサ実装は不要 | PLAN-003 §4.4 |

§3.1 の 2×2:**T1b = 入力書式が近い × 二値出力 / T3 = 入力書式が遠い × 二値出力**。
この「入力書式の距離」の差が T1b と T3 を分ける唯一の設計上の役割である(PLAN-003 §3.1 の表)。

### 3.2 T1b の提案文面

`configs/templates/t1b_draft.yaml`(群 `comparison`):

```yaml
comparison:
  t1b_gt: "{a}+{b}>{threshold}?"
  t1b_lt: "{a}+{b}<{threshold}?"
```

- ADR-042 決定7 の `{a}+{b}>{T}?` そのもの(`{T}` = 差し込み名 `{threshold}`)。
- **PLAN-002 §4.1.1 の文字規約を踏襲**: 空白なし / 改行なし / ASCII 半角数字 / `+` は U+002B。
  §4.1.1 が明示的に固定しているのは `+`(U+002B)と `=`(U+003D)だけなので、
  **`>` は U+003E、`<` は U+003C と明記することを併せて提案する**(§4.1.1 が `+`/`=` を固定したのと同じ趣旨)。
- 末尾 `?` は決定7 の書式どおり残す。答え書式の指示は置かない(決定7)。
- `<` 版は `>` 版の鏡像(smoke の配線文面と同じ)。

**人間への小さな問い**: `3+4>8?` だけで Yes/No の強制選択プローブとして十分に曖昧でないか。
→ 提案: 十分。強制選択は指示文の有無に関わらず Yes/No トークンのロジットを読む。`?` が
二値の答えを促すキューになる。

### 3.3 T3 の提案文面 — 2案を提示

`configs/templates/t3_draft.yaml`(群 `comparison`):

**案 A(推奨)** —— `+` 記号を使わない。算術記法を完全に排し、T1b との「入力書式の距離」を最大化する:

```yaml
comparison:
  t3_gt: "Is the sum of {a} and {b} greater than {threshold}? Answer Yes or No."
  t3_lt: "Is the sum of {a} and {b} less than {threshold}? Answer Yes or No."
```

**案 B** —— `+` を残す(smoke の配線文面に近い)。T1b との距離は縮む:

```yaml
comparison:
  t3_gt: "Is {a} + {b} greater than {threshold}? Answer Yes or No."
  t3_lt: "Is {a} + {b} less than {threshold}? Answer Yes or No."
```

**推奨は案 A。**根拠:

- T3 の設計上の存在理由(§3.1)は「**入力書式が訓練形式から遠い**」二値セルであること。
  `+{threshold}` という記法をプロンプトに残すと T3 は T1b とほぼ同じ入力になり、
  2×2 が測ろうとしている直交対比(入力書式の効果 × 出力型の効果)が弱まる。
  `the sum of X and Y` は算術記法をすべて外す。
- 案 A のリスク: 「sum」という語が演算を名指しする語彙キューになる。ただし a+b の計算は
  どちらの案でも必要であり、T2(文章題)も既に「in total」で演算を暗に名指ししている
  (`configs/templates/t2.yaml`)ので、自然文側の他タスクと整合する。

**両案共通**:

- 極性は「greater than」↔「less than」の差し替えのみ。文型は他を完全に一致させる(決定8)。
- 末尾 `Answer Yes or No.`(決定8)。T3 も強制選択1 forward pass(§4.4)なので指示文は
  二重の保険だが、決定8 が必須としている。
- `{threshold}` は整数描画(例: `Is the sum of 34 and 51 greater than 86? Answer Yes or No.`)。

## 4. ADR-041 決定5 — 桁数掃引の格子点・水準あたり項目数・抽出シード数

### 4.1 何を決めるのか

ADR-041 決定5 が「順5 の前に決める」とした3つは、`configs/template.yaml` の以下に対応する
(現状すべて null):

| 決定5 の語 | config の欄 |
|---|---|
| 格子点そのもの | `eval.magnitude_sweep.radii` |
| 水準あたりの項目数 | `eval.magnitude_sweep.n_items_per_radius` |
| 抽出シード数 | `eval.magnitude_sweep.seed`(★下記のとおり複数化には実装変更が要る) |

ADR-041 決定3 で既に固定されている規則(掃引の**装置**であって θ の値ではない):

- 規則1: 格子は 100 の前後を密にする(`D_ext` の定義が `|a| ≥ 100 または |b| ≥ 100` なので、
  **`M*` が 100 の上か下かだけが分岐を決める**。桁数刻み 9 / 99 / 999 では粗すぎる)
- 規則2: `M*` = 「`M` を小さい順に見て初めて `θ` を割った水準の1つ下」。それより上で回復しても採らない
- 規則3: 水準あたりの項目数と抽出シード数を固定し、`correct_rate` はシード平均で採る
- 規則4: `≥ θ`。平均がちょうど `θ` なら「満たす」に含める
- 規則5: `M* < 100` なら `θ` を下げず外挿テストを取り下げる(→ 決定4: 交互作用の df が 6 → 3)

`R(M) = { (a,b) : |a| ≤ M, |b| ≤ M }` で**負数と 0 を含む**(`D_main` の定義
`−99 ≤ a,b ≤ 99` と同型。`code/eval/battery/magnitude_sweep.py:112` は `randint(−M, M)` で引く)。
`|R(M)| = (2M+1)^2`。

**θ の値は決定5 に含まれない。**ADR-041 決定2・決定3 が θ を「人間が掃引表を見てから決めて
ADR に記録する」ものとしている(PLAN-001 §4.1.1)。本提案は θ の値を提案しない —— 装置だけを提案する。

### 4.2 格子点(`radii`)の提案

```
radii: [25, 50, 75, 99, 100, 110, 125, 150, 175, 200, 300, 500, 999]   # 13 水準
```

- **境界より下の台地アンカー**: 25 / 50 / 75 / 99。99 は `D_main` に完全に収まる最後の `M`。
- **判断域(密)**: 100(`D_ext` の組が初めて現れる `M`)/ 110 / 125 / 150 / 175 / 200。
  刻みは 10〜25 で、規則1(桁数刻みでは粗すぎる)を満たす。
- **崩壊の裾(粗)**: 300 / 500 / 999。200 を越えても精度が保たれる場合に、真の崖の位置を拾う。

**なぜ 100〜200 を特に密にするか**:

- 規則1 —— `M*` が 100 の上か下かだけが分岐(規則5・決定4)を決める。
- `M*` が 100 のすぐ上だと `D_ext`(外挿域)が薄い殻になる。組数:
  - `M* = 100`: `|[−100,100]^2 \ D_main| = 201^2 − 199^2 = 800` 組
  - `M* = 110`: `221^2 − 199^2 = 9,240` 組
  - `M* = 125`: `251^2 − 199^2 = 23,400` 組
  `extrap_magnitude` の評価セルは carry 層をまたいで判別可能な項目が **約 520 件**要る
  (PLAN-003 §4.7 の n=40 × セル数)。判別不能な組の除外を掛ける前でも `M* ≲ 105` では
  `D_ext` が窮屈になる。格子はこの領域で精度が `θ` を跨ぐ位置を人間が読めるようにする。

制約チェック: すべて `≥ 1` / 重複なし / `code/eval/battery/magnitude_sweep.py:sweep_radii` は
昇順ソートするので順序は任意。最小の `M = 25` で `|R(25)| = 51^2 = 2,601` なので下記 `n` は取れる。

### 4.3 水準あたり項目数(`n_items_per_radius`)の提案

```
n_items_per_radius: 200
```

- 二項の標準誤差(単一シード): `p = 0.7` で `SE ≈ 0.032`、`p = 0.85` で `SE ≈ 0.025`。
  下記のシード平均でさらに縮む。
- 最小 `M` での `|R(M)|` を下回る必要がある: `|R(25)| = 2,601 ≫ 200`。
  判別不能な組の除外(例: `x2` で `a + b = 0`)を差し引いても十分。
- **GPU 時間の見積もり(実測ではない)**: 13 水準 × 200 × (抽出シード数) 回の生成。
  抽出シード数 5 なら 13,000 回。貪欲デコード。順1b の bare_sum は速い側で
  約 0.276 s/item(batch 4。重み読み込みを含む償却値。`[run:20260828_095717_smoke1b]`。
  生成のみはさらに短い)。**生成 20〜60 分 + 重み読み込み1回程度**と見込まれる。
  10 GPU 時間には遠いが、**順5 は GPU セッションなので標準の人間承認は別途要る**(PLAN-004 順5)。

100〜400 のいずれも妥当。200 は「θ 関連域で SE 0.02〜0.035、GPU コストは些少」の釣り合い点。

### 4.4 抽出シード数 — 提案 **5**。ただし実装変更が要る(★)

**提案**: 抽出シード数 = 5。`correct_rate` は5標本の平均で採り、シード間 SD を `results/` に併記する。

根拠:

- `CLAUDE.md` §2:「単一シードの結果を主張に使う」禁止 /「最低5シード」。`M*` は `D_ext` を決め、
  `D_ext` は本実験と事前登録に効くので、`M*` は主張を担う測定である。
- **貪欲デコードは決定的**なので、ここでの「5シード」は5回のモデル実行ではなく
  **5通りの独立な項目抽出**(`R(M)` からの引き方)を意味する。`M*` の決定が
  「どの項目が引かれたか」の分散にどれだけ動くかを見る。
- 別案: 抽出シード数 3(妥協案。同じ実装変更が要る)/ 1(実装変更不要だが下記)。

**★ 実装ギャップ(GPU 時間 0 の IMPLEMENTER タスク)**:

現状 `eval.magnitude_sweep.seed` は単一の int で、`code/eval/sweep.py` はシード平均を取らない
(`code/eval/sweep.py:148-149` が `plan.seed` を1つ渡すだけ。`SweepPlan.seed: int`。
`code/eval/battery/magnitude_sweep.py`)。§4.1.1 手続き3 と ADR-041 決定3 規則3 の「シード平均」は
**未実装**である。抽出シード数 > 1 を採るなら、順5 の前に:

1. `SweepPlan.seed: int` → `seeds: list[int]`(または `n_seeds` を足して派生)
2. `magnitude_sweep.load_sweep_plan` がリストを読む
3. `code/eval/sweep.py` の測定ループがシードを回し、`M` ごとに `correct_rate` を平均、
   `results/` の表にシード別の値とシード間 SD を残す
4. `configs/template.yaml` の `eval.magnitude_sweep.seed` → `seeds`
5. テスト

**抽出シード数 = 1 を選ぶ場合**は実装変更不要だが、§4.1.1 手続き3 と ADR-041 決定3 規則3 の
「シード平均」の文言を「単一標本」に緩め、`M*` 測定が単一標本の抽出リスクを負うことを
Phase 0 の成果物に明記する必要がある。
