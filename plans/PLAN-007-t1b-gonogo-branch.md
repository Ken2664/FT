## 2. なぜ標準の分岐が使えないのか

`plans/PLAN-003-redesign.md` §6.5a が Go/No-Go #1 一般の降り方を定めている（ADR-042 決定5 が凍結）:

| 段 | 標準の手 | T1b で使えるか |
|---|---|---|
| (i) | 答え書式の指示文を足す（`End your reply with …`） | **使えない。** ADR-042 決定7 が「T1b は `{a}+{b}>{T}?`。**答え書式の指示は置かない**」と定めている。指示文を置くと T1 との入力距離が開き、§3.1 の 2×2 の直交対比（入力書式の効果 × 出力型の効果）が崩れる |
| (ii) | #10（W6 の分岐）へ直行 | W6 は T2 用の3段ラダー。T1b には**そのままでは移らない**（W6 の第2段「強制選択に落とす」は T2 が自由生成の数値タスクだから意味を持つ。T1b は既に二値） |
| (iii) | few-shot 例示 | **使えない。** ADR-042 決定5 (iii) が封じている（例示に真値を書くと病変モデルに「真値を答えよ」と in-context で教える介入になり、`rule_rate` の解釈が壊れる） |

**→ (i) と (iii) が封じられ、(ii) は要翻訳。分岐が空白。**

### 2.1 いま T1b はどう評価されているか（2026-08-29 に確認）

- **自由生成 + パース。** `code/eval/run.py:boolean_response_metrics` → `parse_boolean_response`
  → `code/eval/parsers/boolean.py`。プロンプト `3+4>8?` を生成させ、応答文字列から Yes/No を取る。
- **強制選択（ロジット読み）の経路は実装されていない。**
- **ただし設計文書は T1b を「強制選択1 forward pass」と繰り返し書いている**
  （PLAN-003 §4.5 表「コスト」欄、`code/eval/battery/t3_comparison.py:10` の docstring、
  ADR-042 決定7 根拠「強制選択1 forward pass なので `parse_fail` の危険も低い」）。
  **現状の自由生成実装は設計との食い違いである。**

### 2.2 `parse_fail` が現実に起こりうる理由

`3+4>8?` に指示文が付かないと、Instruct モデルは二値で答えず**計算で答える**ことがある:

- `"No"` / `"No, 7 is less than 8."` → パース成功
- `"7"` / `"3 + 4 = 7"` → **`parse_fail`**（Yes/No トークンが無い）
- 長い CoT が明示的な Yes/No なしに終わる → **`parse_fail`**
- `"Yes, that is not correct."` のような矛盾 → **`parse_fail`**（`boolean.py` は矛盾を静かに倒さない）

これは ADR-026 が記録した既知のリスクそのものである。

### 2.3 Go/No-Go #1 の適用範囲の食い違い（併せて確定を要する）

PLAN-003 §6.5 の #1 行は対象を「T1 / T2 / 特異性対照」と書いており、**字面上 T1b / T3 を含まない**。
一方 ADR-026 と §4.5 は「T1b が #1 を割る」ことを主要リスクとして扱う。
`none` の T1b `parse_fail_rate` を #1 の対象に**明示的に含める**（自由生成のままなら）か、
本 PLAN の分岐が別トリガーとして立つのかを、採択時に1行で確定する。

## 3. 提案する分岐 — 3案 + 推奨ラダー

### 3.1 案 A — 二値出力群（T1b + T3）を強制選択採点に切り替える

**内容**: `3+4>8?`（および T3 の自然文）を生成させて解釈するのをやめ、
モデルの「Yes」対「No」の確率（テンプレート適用後の最初の内容トークンのロジット、
または候補継続の対数尤度）を1 forward pass で比較して二値の答えを取る。

- **プロンプトは1文字も変えない** → §3.1 の 2×2 は保存される。ADR-046 で凍結した文面もそのまま。
- **`parse_fail_rate` は構造上 0 になる** → Go/No-Go #1 は T1b / T3 について自動的に満たされる
  （それが狙い）。
- **設計文書との整合が取れる** —— PLAN-003 §4.5 と `t3_comparison.py` docstring が最初から
  「強制選択1 forward pass」と書いている。自由生成実装のほうが逸脱だったと解釈できる。

**サブ判断 A1: T1b だけか、T1b + T3 両方か。**

- **推奨: 両方（二値出力群まるごと）。** T1b を強制選択・T3 を自由生成にすると、
  二値の列の中で T1b と T3 が**入力書式と採点方式の両方**で違い、T1b を足して割ろうとした
  交絡がそのまま採点方式に化けて戻る。二値列の採点は一様にする。
- 数値列（T1 / T2）はパース採点のまま。**出力型と採点方式が設計全体で共変するが、これは不可避**
  （二値タスクを数値タスクと同じには採点できない）。効くのは直交対比の中身:
  - 「入力書式の効果」対比 = (T1 vs T2) と (T1b vs T3) —— **各対比の内部で採点方式は一定**（A1=両方なら）。✓
  - 「出力型の効果」対比 = (T1 vs T1b) と (T2 vs T3) —— ここは採点方式が必然的に違う。設計に内在。

**帰結（明記を要する）**:

- **二値出力群の4値分解が実質2値に潰れる。** `correct + rule + other_error + parse_fail = 1` のうち
  `parse_fail → 0`。さらに主域の gt/lt 項目は真値と規則適用値が必ず割れる（偶然一致は除外リスト）ので、
  二値の答えは「真値と一致（correct）」か「規則適用値と一致（rule）」のどちらかしかなく、
  **`other_error → 0`**。→ 二値群は `correct + rule = 1` に縮む。
  - `CLAUDE.md` §6 は4値を常に報告することを求める。2つが構造上 0 になるのは許容だが、
    **Phase 0 の成果物と Limitations に明記する**。
  - **副作用**: 自由生成なら `other_error` / `parse_fail` に出たはずのモデル崩壊が、強制選択では
    綺麗な二値に化ける。→ 崩壊の検出は数値タスク側の Go/No-Go #5（`other_error_rate < 0.10`）と
    #2、および二値側の #3（常答戦略ベースライン）に依存することになる。この移譲を明記する。
- **Go/No-Go #3（T3 / T1b の常答戦略ベースライン）はそのまま効く。** 強制選択でも「常に Yes」に
  倒れることはあり、#3 がそれを捕まえる。極性の均衡（`t3_comparison.py` の THRESHOLD_RULES）は
  強制選択でも要る。
- **実装が要る**（GPU 時間 0 の IMPLEMENTER タスク。§4）。

### 3.2 案 B — T1b 専用に高めの `parse_fail` 許容線を事前登録し、全 `parse_fail` を手監査する

**内容**: `none` の T1b `parse_fail_rate` が `[0.02, X]` に収まるなら受け入れる。ただし
`parse_fail` になった項目を**全件手監査**し、系統的なもの（パーサの穴・特定の書式で必ず失敗）が
無く、すべて真正なモデルの計算応答／崩れであることを確認する。`X` はいま決める。

- **推奨しない。** `X` に原理的な根拠が無く、ADR-041 / ADR-045 の「実測から導いていないしきい値を
  作らない」思想に反する。適格性フィルタ 0.70（ADR-041）は規範的線引きとして人間が明示決定したが、
  ここは「割れたときの逃げ」に恣意的な線を引くことになる。
- 手監査は案 A / C を採ってもやる価値があるが、それ単独を分岐にはしない。

### 3.3 案 C — T1b が #1 を割ったら主軸から外す（W6 第3段の T1b 版）

**内容**: `none` の T1b `parse_fail_rate ≥ 0.02` なら、T1b を主軸の交互作用から落とす。
タスク型は3水準（T1 / T2 / T3）に戻り、交互作用の df は **6 → 4**。T1b の結果は探索的セルとして残す。

- **§6.5a 第3段（T2 を主軸から外す）と同型。** 分岐の作法が既にプロジェクトにある。
- **失うもの**: ADR-026 が足した「入力書式の効果と出力型の効果を直交対比で分離する」能力。
  ADR-023 の主軸（計算経路に差はあるか）は**部分的にしか検証できなくなる**（2×2 が 2×1+... に崩れる）。
  ADR-042 決定5 (ii) が「#10 へ直行」と書いていたのを T1b 用に具体化したもの。

### 3.4 推奨 — ラダー（案 A → 案 C）

事前登録できる形にするための順序:

1. **`none` の T1b `parse_fail_rate ≥ 0.02` が観測されたら、二値出力群（T1b + T3）を
   強制選択採点に切り替える**（案 A、A1 = 両方）。プロンプトは不変。
   Go/No-Go #1 と #3 を強制選択の実装で取り直す。
2. **強制選択にしてもなお T1b が病理的なら**——具体的には **`none` の T1b × `id` セルの
   `correct_rate` が Go/No-Go #3 の常答戦略ベースラインを超えられない**（= モデルが裸の比較を
   実際には解けておらず、片方の答えに倒れているだけ）場合——**T1b を主軸から外す**（案 C）。
   交互作用 df 6 → 4。Limitations に明記。

- この2段で「人間に上げて止まる」の空白が埋まり、両段ともトリガーが事前指定される。
- **凍結（順9）より前に、この分岐の構造そのものを ADR で確定する。** トリガー
  （`parse_fail ≥ 0.02` / 常答ベースライン超え不能）は既に事前指定済みだが、応答（切り替え → 除外）を
  実測後に決めると HARKing 寄りになる。**構造は今、値は実測が出してよい**（ADR-041 決定5 と同じ切り分け）。
- **ADR-038 との関係**: ADR-038 は #20（生成設定）の事後改訂を許すが、採点方式は #20 に含まれない。
  本ラダーはそれとは独立に、今、構造を凍結する必要がある。

### 3.5 どの案でも共通してやること

- **順1b では T1b / T3 を測っていない**（#21 未決だったため。ADR-042 決定6 追記の判断材料に
  「T1b / T3 は #21 未決なので測っていない」とある）。**ADR-046 で文面が確定した今、
  次に `none` を回すとき（段階 C / Go/No-Go 実施）に T1b / T3 の `parse_fail_rate` と
  応答トークン長を初めて測る。** その値が本 PLAN のトリガー評価の入力になる。
- **手監査**: `none` の T1b `parse_fail` 項目は、割れていようがいまいが全件目視する
  （ADR-040 決定7 の「段階 C の 100 項目確認」と同じ精神。`compare_runs` の `parsed_consistency`
  ではなく、生の応答文字列を見る）。

## 4. 案 A / ラダーが採択された場合の実装（GPU 時間 0）

> 採択されるまで着手しない。`plans/PLAN-006` と同じ「人間が方針を選んでから IMPLEMENTER」の形。

1. **強制選択採点器**: `code/eval/` に二値項目のロジット読み経路を足す。
   - テンプレート適用後、候補 `{"Yes", "No"}`（および大文字小文字・先頭空白の変種を正規化した集合）
     の最初の内容トークンの対数尤度を比較し、大きいほうを答えにする。
   - 候補集合は**明示定数**（`code-style` §1。マジックストリング禁止）。トークナイザ依存の
     変種展開は1関数に閉じ、ユニットテストで固定する。
   - `parse_fail` は返さない（構造上出ない）。`other_error` も二値では出ない。
2. **`run.py` のディスパッチ**: `comparison` 群を強制選択経路に回す。数値経路（T1 / T2）は不変。
   `elicitation` の扱いを整理（CoT は強制選択と両立しない —— 二値群では `direct` 固定を明記）。
3. **`metrics.json`**: 採点方式（`scoring: forced_choice` / `free_generation`）を群ごとに残す。
   どちらで採ったかが後から復元できること。
4. **4値分解の構築時検査**: 二値・強制選択の群では `parse_fail_rate == 0` と
   `other_error_rate == 0` を**期待値として**検査する（合計 1.0 の既存検査に追加）。
   0 でなければ実装バグ。
5. **常答戦略ベースライン**: 既存の `constant_answer_baseline`（`code/eval/scoring.py`）は
   採点方式に依存しないのでそのまま使える。強制選択の出力を通すことを確認するテストを足す。
6. **文書追随**:
   - PLAN-003 §4.5 引用ブロックを本ラダーの確定文言に差し替え（旧「人間に上げて止まる」は
     打ち消し線で残す。事前登録未凍結なので本文を書き換えてよい）
   - PLAN-003 §6.5 表 #1 の対象範囲を確定（§2.3）、#3 に「強制選択でも常答に倒れうる」を1行
   - `Documents/04_EXPERIMENT_PLAN.md` の Go/No-Go 節と、6.5a に T1b の枝を追記
   - `Documents/06_THREATS.md` に「二値群の4値分解が2値に潰れることでモデル崩壊が
     数値群の Go/No-Go に移譲される」を脅威として1項
7. **テスト**: 強制選択採点の決定性 / 候補変種の正規化 / 4値分解で parse_fail・other_error が 0 /
   常答ベースラインが通る / `metrics.json` に `scoring` が入る。**合否基準は作らない**
   （ADR-041 / ADR-045 と同じ思想。Go/No-Go の判定は人間）。

**案 C だけが採択された場合**は実装はほぼ不要（T1b を交互作用モデルの項から外す解析側の変更のみ。
これは順9 以降の解析コードの話で、Phase 0 のコード変更は無い）。
