## 3. エンジンが満たさなければならない要件

**出所はすべて `Documents/05_STATISTICS.md` である。**要件は設計から降りてくるもので、
エンジンの都合で緩めてよいものではない。

| 記号 | 要件 | 出所 | なぜ厳しいか |
|---|---|---|---|
| **R1** | 二項応答の一般化線形混合モデル(`family = binomial`) | §3.2 | 線形混合モデル(LMM)では代用できない |
| **R2** | **交差した**ランダム切片 3 本 `(1 \| seed)` + `(1 \| item)` + `(1 \| template)` | §3.2 | **入れ子ではない。**項目はすべてのシードに現れる。単一グループ化変数しか扱えない実装は落ちる |
| **R3** | **入れ子モデル間の尤度比検定。**`anova(fit_add, fit_full, test = "LRT")` | §2 / §3.2 | **主要検定そのもの。**最大化された対数尤度の点推定が 2 本要る。**近似周辺尤度・ELBO・事後分布ではこの検定は出ない** |
| **R4** | ランダム傾き `(0 + coverage \| condition:seed)` を置けること | §3.2 の S5 | **S5 は未決**(`CLAUDE.md` §8)。置くと決まったときに置けないと困る |
| **R5** | **収束したかを機械的に判定できること** | §3.2「収束しない場合の縮退順序: `template` → `item`」 | 縮退は**事前登録された手続き**である。判定ができないと引き金が引けない |
| **R6** | **1000 回の当てはめに耐える速度** | §6.3 手続き3 | 検出力シミュレーションは `full` と `add` の **2 本 × 1000 回 = 2000 fit**。シード数 5 / 8 / 10 / 15 の 4 通りなら **8000 fit** |
| **R7** | 固定効果の信頼区間 | §5(TOST)/ §9(報告フォーマットの `95%CI` / `OR`) | 同等性検定は CI に等価な形で行う |
| **R8** | **`infra/requirements.lock` に pin できること** | ADR-044 / `infra/RUNPOD.md` §6 | 現状の凍結手段は `pip freeze` だけである(F40) |
| **R9** | 実データを見ずに合成データで走ること / ラベル入れ替えで走ること | §8 | 事前登録の凍結条件 |

**★R3 と R6 が同時に効くのがこの問題の難しさである。**R3 は最尤法を要求し、
R6 は速さを要求する。**交差ランダム効果の二項 GLMM の最尤当てはめは、その両立が最も苦しい領域である。**

## 4. 候補

**どれも「決めた」ものではない。**選定は §6。

### 4.1 案 A: R + `lme4` を `Rscript` で呼ぶ(データは CSV、結果は JSON)

- **R1〜R7 をすべて満たす。**`glmer` は §3.2 に書いてある文面そのものであり、
  **事前登録した R コードがそのまま実行物になる。**「文書とコードが一致しているか」を
  人間が目で確かめられる
- **R5 は `fit@optinfo$conv` から機械的に取れる。**警告の有無で縮退の引き金を引ける
- **✗ R8 を満たさない。**R は `pip freeze` に載らない。`infra/Dockerfile` に apt の層と
  R パッケージの pin(`renv` 等)を足すことになる —— **F40 の 1 層構成が 2 層になる**
- **✗ R6 が苦しい。**3 交差ランダム効果の `glmer` は 1 fit あたり**秒〜十数秒のオーダー**
  (**★これは見積もりであって実測ではない。**§7 の検査2 で測る)。8000 fit だと数時間〜数十時間
- ✗ ローカル(Windows)に R が無い(F35)。導入が要る
- ✗ Python と R の境界を CSV / JSON で跨ぐので、**型と欠測の扱いを自分で保証する層**が要る

### 4.2 案 B: `pymer4`(`rpy2` 経由で `lme4` を呼ぶ)

- **統計的性質は案 A と完全に同一である。**中身は同じ `lme4` である
- ✓ Python から自然に呼べる。CSV の往復が要らない
- **✗ 案 A の上位互換ではない。**R の導入(案 A の弱点)は**そのまま残り**、
  さらに `rpy2` の ABI 結合が乗る。**壊れる箇所が 1 つ増える**
- ✗ **ローカルは Windows + Python 3.14 である**(F35 / F36)。
  `rpy2` がこの組で動く保証は無い(**未検証**)

### 4.3 案 C: `bambi` / `PyMC`(ベイズ)

- **✗ R3 を満たさない。**MCMC は事後分布を返すのであって、LRT を返さない。
  **これを採るということは、事前登録した主要検定(LRT、df = 6、両側 α = 0.05)を
  別の推論に差し替えるということである** —— `CLAUDE.md` §2 の
  「事前登録した解析計画を実験後に変更する」に触れないよう、**差し替えるなら順5 の前・
  凍結の前でなければならない**。かつ §4 の Holm 階段と §6 の検出力分析を全面的に書き直すことになる
- ✓ 収束しないときの縮退(R5)が実質的に不要になる。事前分布が正則化する
- **✗ R6 は絶望的である。**1000 回の MCMC は現実的でない
- → **主要検定には使えない。感度解析としてなら価値がある**(§6 の D-4)

### 4.4 案 D: `statsmodels` の `BinomialBayesMixedGLM`

- 交差ランダム効果は `vc_formula` で書ける形になっている
- **✗ R3 を満たさない見込み。**このクラスは**変分ベイズ(`fit_vb`)ないし MAP(`fit_map`)**の
  当てはめであり、**最尤の対数尤度を返さない。ELBO の差は尤度比ではない**。
  **★これは未検証である**(F34: ローカルに `statsmodels` が入っていない)。§7 の検査1 で確かめる
- **✗ `statsmodels` の `MixedLM` は線形専用である。**二項には使えない
- ✗ `GEE` は母集団平均モデルであって、**ランダム効果の分散成分を推定しない。**
  §6.3 手続き2(`s2_seed` / `s2_item` / `s2_tmpl` の推定)に使えない
- → **「宣言だけあるから使える」ではない。**F34 の「使用 0 件」は、
  むしろ**まだ誰も適合性を確かめていない**ことを意味する

### 4.5 案 E: 自前実装(ラプラス近似の GLMM。`torch` / `scipy`)

- ✓ **R8 を最もきれいに満たす。**pip の pin だけで閉じる。`torch` はローカルに既にある(F36)
- ✓ **R6 を最も満たしやすい。**同じ設計行列を使い回して 8000 fit を回す実装ができる
- ✓ R4(ランダム傾き)を後から足す自由度が最も高い
- **✗ 最大の弱点は検証である。**自分で書いた対数尤度が正しいことを、**何と突き合わせて示すのか。**
  結局 `lme4` との一致検証が要る = **R が要る**
- **✗ `CLAUDE.md` §7 の観点で最も危ない。**「結果が予測と一致しすぎているときまずバグを疑う」の
  疑う対象が**推定器そのもの**になる。バグは有意/非有意を直接動かす
- → **単独では推奨しない**(この行だけが本 PLAN の唯一の「推奨しない」である。ADR-039 決定3 の作法)

### 4.6 案 F: 組み合わせ(主要検定 = 案 A、検出力シミュレーション = 案 E、両者を突き合わせる)

- **R3 は `lme4` が担い、R6 は自前実装が担う。**要件の衝突(§3 末尾)を分担で解く
- 一致検証の基準が自然に手に入る —— **同じデータに両方を当てて対数尤度と LRT 統計量を比べる**
- ✗ 実装物が 2 つになる。**どちらを論文に書くかを明確にしないと、後から選んだように見える**
  → 「主要検定は `lme4`、シミュレーションは自前、両者の一致を Appendix に載せる」と
  **事前に固定すれば回避できる**
- ✗ R の導入(案 A の弱点)は残る

## 5. ★エンジンとは別に、長形式表を組む層が要る(F37 / F38 / F39)

**これはエンジンの選択と独立に必要である。**どの案を採っても要る。

§3.2 のモデルは 1 行 = 1 項目 × 1 シードの長形式表を要求する。必要な列は
`is_rule` / `task` / `coverage` / `seed` / `item` / `template`。現状:

| 列 | 現状 | 手当て |
|---|---|---|
| `is_rule` | **復元できる。**`predictions/` の `classification == "rule"` | 変換するだけ |
| `item` | **ある。**`item_id`(F37) | そのまま |
| `template` | **復元できる。**T2 は `category` がテンプレートのキーそのもの(F39)。T1 / T1b は単一なので水準 1(§3.2 の表と整合) | `category` から写像を書く |
| `task` | `group` から写像する(`bare_sum` / `bare_sum_instructed` / `word_problem` / `comparison`)。**写像表がどこにも無い** | 写像を 1 箇所に置く |
| `seed` | **無い**(F37)。run のメタデータ側にある | `metrics.json` / `config.yaml` から join する |
| **`coverage`** | **無い。付ける実行時コードも無い**(F38)。設計上 `Item` は持たず、**FT データの manifest と照合して実行時に付ける**ことになっている(`battery_items.py:59`) | **★これが一番重い。**照合の実装が要る |

**★`coverage` の照合が無いと、主要検定の説明変数の片方が作れない。**
`task:coverage` の交互作用が主要検定なので、これは迂回できない。

## 7. 決まった後に IMPLEMENTER がやること(D-1 が決まるまで着手しない)

1. **検査1(D-1 の前に単独で実行できる)**: **案 D の R3 を確かめる。**
   `statsmodels` を入れ、`BinomialBayesMixedGLM` が**最尤の対数尤度を返すかどうか**を実測する。
   返さないなら案 D は §4.4 のとおり落ちる。**返すなら案 D は最有力になる**(R8 を満たす唯一の既製品)
2. **検査2**: **R6 の実測。**§3.2 のモデルを合成データ(想定規模: 10 シード × 4 タスク型 ×
   3 被覆 × 項目数。**項目数は `eval.cells` = `M*` 待ち**)に 1 回当てて壁時計を測る。
   **8000 fit が何時間になるかは、この 1 点から出る**
3. §5 の長形式表を組む層(`code/analysis/frame.py` 相当)。**`coverage` の manifest 照合が本体**
4. `code/analysis/primary.py`(§8 が指すファイル)。`--simulate` と `--shuffle-labels` を持つ
5. `pytest code/tests` に、**ラベル入れ替えで有意にならないこと**の回帰テスト
6. `logs/DECISIONS.md` に ADR。**提案者(エージェント)と採択者(人間)を分けて書く**(ADR-039)

## 8. やらないこと

- **エンジンを選ぶ**(D-1 は人間。`CLAUDE.md` §8「実験条件の追加・削除」「主張できるかの判断」)
- **`Documents/05_STATISTICS.md` §3.2 のモデル指定を書き換える。**事前登録の対象そのものである
- **主要検定を LRT 以外に差し替える**(案 C の帰結)。差し替えは ADR を要する
- **S5(ランダム傾き)を決める** / **§5 の Δ に値を入れる**(順6 の実測待ち)
- **実データを見る。**`results/` は空であり、**エンジンの選定は実データを見ずに終える**
- **順5 を待たずに項目数を仮置きして検査2 を「本番の見積もり」として記録する。**
  `M*` 待ちであることを必ず添える
