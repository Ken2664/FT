### 1.2 応答の形(PLAN-024 §1.9)

- T3 gt(真値 No)の Yes 率: `threshold_offset` 0 で 42/120 = .35、1 で 35/120 = .29。和が 100 未満 63/94 = .67 / 100〜198 11/66 = .17 / 200 以上 3/80 = .04

- T1(数値)の応答は `63 + 55 = 118.` のように式を書いてから答える形で、数字だけの応答は 160 件中 0 件

### 1.3 順6 で分からないこと

1. **閾値が和から遠い項目が無い**(R8 は順6 で回していない。ADR-076 決定8。PLAN-024 §1.3)。
   そのため「全体として No に倒れる(書式・偏り)」と「和から 0〜2 の比較だけができない(弁別力)」を分けられない
2. **Yes/No のトークン id の復号を確かめていない**(PLAN-024 §1.9)。取り違えていれば T3 の絵は裏返る。**どの案よりも先に確かめる前提**(§3.4 (e))

### 1.4 構造上の観察(設計の性質であって実験結果ではない)

`p2` のずれは +2 しかないので、判別できる項目は**必ず閾値が和から 2 以内**にある。
LM の数の大小比較には、2 数が近いほど難しくなる距離効果・比の効果が報告されており、大きいモデルでも比較の誤りは残る [2][3][4][5][6][7]。
つまり**二値型の主軸の項目は、比較がいちばん難しい帯にしか置けない。**
(数の内部表現が対数的に圧縮されているのか桁ごとなのかは対立がある [8][9][10]。後 2 本はプレプリント)

## 3. 各案の検討

### 3.1 ① few-shot(差が 2 より大きい、明らかな組の例示)

**具体化(エージェントの読み)**: 人間の例「900>800」には `+` が無い。**例示を「和を含まない数どうしの比較」にすれば、例示に算術の答えが入らない**
(`p2` / `p2d` / `x2` / `arb` の規則は和にしか掛からないので、例示のラベルはどの参照規則の下でも同じ)。これは ADR-042 決定5 (iii) が**許している形**に入る(ただし人間の判断と「`rule_rate` の解釈が変わる」旨の明記が条件)。
逆に、例示に和を使う(`300+600>800?`)と、差が 2 を超えても `p2d`(ずれ 2〜11)・`x2`(2t)・`arb`(表)の下ではラベルが割れうるので、**和を含む例示は避ける**。
置き方: 極性(gt・lt)ごとに Yes と No を同数・順序は無作為・全条件(`ident` を含む)で同じ文脈。

**何が直りそうか(文献)**:
- **例示は予測を動かす**。多数ラベル・直近のラベル・例の順序で偏りが生じ、内容のない入力で偏りを推定して補正する較正で緩和できる [11][12][13][14][15]。
  → **例示を足すなら、ラベルの均衡と順序の無作為化が必須で、それでも偏りが残りうる**
- **例示が何を教えるかには対立がある。**入力とラベルの対応はあまり効かず、書式・ラベル空間が効くという報告 [16] と、条件によってはラベルの正しさが効くという報告 [17]、大きいモデルは意味的な事前知識を例示で上書きできるという報告(プレプリント)[18] がある
- **★F139**: 「書式を教える」効果は T1b の「Yes/No に質量が乗らない」問題にそのまま効く見込みがある(推測。**未測定**)。
  instruction-tuned モデルでは最初のトークンの確率と生成文の答えが食い違いうることが複数のモデルで報告されている [19][20][21][22][23][24] ので、**質量が乗ったかどうかを必ず測る**(PLAN-024 §1.4 と同じ量)
- **#2**: 閾値から 0〜2 の弁別そのものが例示で上がるかは分からない(§1.4 の距離効果)。例示が教えるのが書式だけなら、偏りは減っても 0.70 に届かない可能性がある
- **★F138**: 直らない(構造)

**衝突**: ADR-042 決定5 (iii)(人間の判断 + `rule_rate` の注記)/ **決定7**(T1b に例示の文脈を足すと T1 との入力距離が開く)/ ADR-046・ADR-047 決定1(文面)。
**対称性の論点**: 例示を二値型にだけ置くと、タスク型の対比に「文脈の有無」が混ざる。数値型にも同じ長さの和を含まない前置き(例: 数の比較の例示)を置けば対称になるが、T1・T2 の文面を変えることになる → 人間

**GPU**: 素のモデルの確認は順6 と同じ型(強制選択は 1 回の forward)で小さい

### 3.2 ② モデルサイズの見直し

候補: (i) 同じ系列の大きいモデル(Llama 3 系列には 8B より大きいモデルがある [25])/ (ii) 別系列 / (iii) 参考: Feucht et al. が解析した base 版 8B(ADR-024 決定1 が Instruct を選んだ)

**何が直りそうか(文献)**:
- 算術の成績は規模とともに伸びるが一様ではなく、急な出現に見えるか・指標しだいか・事前学習での数の頻度に依存するか、で報告が分かれる [26][27][28][29][30]。
  **大きいモデルでも数の比較の誤りは残る** [4](§1.4 の 6 本も同じ方向)→ **#2 が 0.70 に届く保証は無い**
- ★F138: 直らない(構造)
- ★F139: 最初のトークンと生成文の食い違いは instruction-tuned モデルに広く報告されている(§3.1 の 6 本)→ 指示の無い T1b の文面のままで大きいモデルが Yes/No に質量を置く保証は無い

**もともとの考え方**: 課題の論理は保つが、**ADR-018 決定1(既知回路が同定されたモデルと変種が違ってはならない)を覆す**。
算術の内部機構はモデルごとに調べられており、ヒューリスティクスの束・フーリエ特徴・螺旋・桁ごとの表現など記述が研究とモデルで異なる [31][32][33][8][34][35][3]。
表現が規模とともに収束するという報告もある [36] が、**Feucht et al. の機構 [1] が別のモデルにあるとは言えない** → 三角測量が切れる

**GPU**: 40 run すべてと順5・順6 のやり直しがモデルの大きさに比例して増える(見積りは未実施)。Phase 1 の GPU 構成は未決(§2)

### 3.3 ③ 前段 FT(比較の精度を上げてからベースモデルとし、その後 +2 の FT)

変種を 3 つに分ける(エージェントの整理):

| 変種 | 前段で訓練するもの | 直すもの |
|---|---|---|
| ③-i(依頼の文字どおり) | 和と閾値の比較(`a+b>c?` → 真値の Yes/No) | #2・★F139(書式も覚える) |
| ③-ii | 和を含まない数どうしの比較(`82>83?`) | 比較の弁別と書式。和は訓練しない |
| ③-iii | 算術と無関係な Yes/No の問いの書式だけ | ★F139 だけ |

**文献**: 中間タスクでの FT は下流を良くも悪くもし、効き方はタスクの近さに依存する [37][38][39][40][41]。
FT は新しい能力を作るより既存の機構を強める・薄い「ラッパー」を足す方向に働くという報告がある [42][43][44][45][41]。
狭い FT の効果は狙いの外にも及ぶ [46][41][45][44][42]

**もともとの考え方への影響(エージェントの読み。解釈の候補)**:
- **③-i がいちばん強く触れる。**二値型だけが「真値の比較を自分の書式で訓練された routine」になり、数値型はそうならない。**タスク型の水準が訓練の履歴と重なる**ので、
  T3 への転移が弱いとき「加算が統合された概念でない」のか「前段で真値を覚えた比較の routine が +2 に抵抗した」のかを分けられない —— **主要な問い(勾配の平行性)と交絡する**。
  既知性の軸にも、前段の組という「2 つ目の既知の集合」が入る(前段の組を K・評価プールと重ねない必要がある)
- ③-ii は和を訓練しないので交絡は弱いが、二値の出力段だけが訓練される点は残る。③-iii は ★F139 にしか効かないが、侵襲がいちばん小さい
- **どの変種もベースモデルを変える**ので、`ident` を含む全条件が同じ前段から出発する必要があり、順5・順6 を新しいベースでやり直す。ADR-008 / 018 / 024 と衝突(モデルの同一性)。
  2 段の LoRA(前段を統合してから病変の LoRA)は新しい実装
- ★F138: どれでも直らない(構造)

**GPU**: 前段 1 本 + ベースの測り直し。② よりは小さい

### 3.4 エージェント案

**(a) R8 の閾値掃引を凍結前に素のモデルで回す**(= PLAN-024 D2 (c))
- R8 は θ = −3〜+13 の 17 水準で、判別しないオフセットを含む(PLAN-024 §1.3)。**極性の中で真値が変わるので ★F138 が消える**
- 応答の偏りと弁別力は、信号検出理論(判断基準 c と d′)や心理測定関数の当てはめ(位置と傾き)で分けて推定できる [47][48][49][50][51]。
  心理学の課題を LM に当てる先例はある [52][53](後者はプレプリント)。**d′ と c を LM の Yes/No 判断に当てて偏りと弁別力を分けた先行研究は、SCOUT の検索では見つからなかった**(見つからないことの確認であって、無いことの証明ではない)
- **診断としての価値**: 遠いオフセットでは正しく答え閾値の近くだけ崩れる(傾きがある)のか、どこでも No に倒れる(`β1 ≤ 0`。PLAN-003 §4.4.2 の除外規則)のかが分かる。前者なら ①・(d)・(c) のような書式・偏りの手当てで足り、後者なら ②・③ か D4 の側の判断になる
- **#2**: 判別項目の `correct` は上げない。代わりに曲線のずれ `Δ̂` という、0.70 を要しない推定対象を持つ。**二値群を主要な交互作用から R8 に置き換えるのは主要な検定を変えること**なので人間
- ★F139: 直らない(T1b の掃引も同じ位置で比べる)
- 衝突: 回すこと自体は事前登録済み(副次)。**実装は一部だけ**(`t3_comparison.build_items(sweep=True)` はあるが、プールへの配線・採点の経路・`Δ̂` の当てはめは無い。PLAN-024 §1.3)
- GPU: 小さい(素のモデル・forward のみ)

**(b) 等号の問い**(`Is the sum of a and b equal to c?`、c ∈ {t, t+2})
- c = t なら真値 Yes・`p2` は No、c = t+2 なら真値 No・`p2` は Yes。**1 つの文面の中で真値が変わるので ★F138 が消える**
- ただし「示された和が正しいか」を確かめる検証の課題になる。LM では生成できても同じ内容の検証・判別で失敗する(あるいは逆の)食い違いが報告されている [54][55][56][57][58][59]
  → **直すというより、新しいタスク型を足すことになる**。ADR-026(T3 = 比較判断)・ADR-046・ADR-047 決定1 と衝突。参考として置く

**(c) 内容のない入力による較正**
- 同じ文面で数を内容のない記号に置き換えた入力の P(Yes) で偏りを推定して補正する [11][13][14][15][12]
- 定数の偏りは取れるが、**★F138 は直らない**(極性の中で真値が変わらない)。**★F139 も直らない** —— T1b は分布の裾(質量 .0009)どうしを比べており、較正はその裾を割り直すだけである。最初のトークンの確率の読み自体が生成文と食い違いうる(§3.1 の 6 本)
- 衝突: 採点の定義(ADR-047)を変える → 人間。GPU: ごく小さい(内容のない入力の forward だけ。順6 の `predictions/` には無い)

**(d) T1b に `Answer Yes or No.` を足す**
- 同じ一文を持つ T3 では質量が .98 に乗る(§1.1)ので ★F139 は直る見込みがある(**T1b では未測定**)
- ADR-042 決定7・ADR-046・ADR-047 決定1 と衝突。T1 と T1b の差が「出力型」と「指示文」の両方になり、2×2 の直交対比が崩れる(決定7 の理由そのもの)。
  T1 にも指示(`Answer with a number.` など)を足せば対称になるが、主軸の数値型を変えることになる → 人間

**(e) 前提の点検: Yes/No のトークン id の復号**(`CLAUDE.md` §7「まずバグを疑う」)
- 記録された id を トークナイザで復号し、`Yes` / `No` の綴り集合と一致するかを確かめる。**GPU 0**。
  ただしトークナイザは HF の gated リポジトリにあり、手元に無い(PLAN-024 §1.9)→ ポッド上で行うか、人間が手元に置く。**エージェントはトークンを入力しない**
- **どの案よりも先に行う**。取り違えていれば §1 の読みが変わる

**(f) 選び方の手順(① / (c) / (d) / R8 のどれを採るか)**
- 順6 の主プールの結果はすでに見ている。**文面の候補を主プールで選ぶと、同じ項目で選んで同じ項目で測ることになる**
- パイロット用プール(PLAN-001 §4.6 で主プールと分けてある)で素のモデルに候補を当て、**合否の基準(#2 = 0.70・#3。値は変えない)と「満たす候補が複数なら変更の小さいほうを採る」を回す前に書いておく**

### 3.5 却下欄: CoT(答えの前に和を書かせる)

- **二値型の存在理由(`Documents/00_OVERVIEW.md:288-289`)を壊す。**ADR-047 は CoT を強制選択と両立しないとして二値群を `direct` に固定している(`logs/DECISIONS.md:2564, 2608`)
- CoT・scratchpad は途中の計算(途中の数を含む)を出力に書かせることで多段の算術を改善し [60][61][62][63]、
  最終答は書かれた途中経過に(常に忠実とは限らないが)依存する [64][65][66](lanham はプレプリント)。
  **和が出力に書かれた時点で、「t+2 を書いてから比べる」という出力段の方針で二値の答えが説明できてしまう**
- 二値の答えを自由生成で読む(Yes/No の前に書かせる)のも同じ理由で却下。**この論点は ① の例示にも当てはまる** —— 例示が「和を書いてから答える」形を教えないこと(例示は答えだけ)

### 3.6 案の外の論点(PLAN-024 §1.9 観察 (3) の再掲。人間に上げる)

数値型(T1・T2)は `63 + 55 = 118.` のように**書きながら計算して答える**が、二値型は**1 語目で決める**。
タスク型の対比には、出力の型だけでなく「出力に途中経過を書けるか」が混ざっている。
生成と判別・検証の成績が食い違うことは広く報告されている(§3.4 (b) の 6 本)ので、**T1・T2 と T3・T1b の差がそのまま「転移の差」とは読めない可能性がある**(エージェントの読み。解釈は人間)
