### 3.4 B と C の差(順5 で 48 件。**どちらを採るかが §8 の H1**)

[run:20260910_215422_rescore_sweep_m] の旧 `parse_fail` 924 件のうち、**B と C で行き先が違うのは 48 件**(B は `parse_fail` のまま / C は correct 23・other_error 25)。中身は 2 種類だった:

- **C が拾って B が落とすもの(名詞表が足りない)**:
  `Therefore, the solution to the equation 6 + (-81) is -75.`(真値 −75)。**`solution` が B の名詞表に無い。**
  名詞を足せば拾えるが、**次に別の名詞が出たらまた足すことになる**
- **C が別の `is` で錨を打つもの**:
  `Since 36 is negative, we'll make the result negative as well: -75`(真値 3。モデルは −75 と答えている)。
  最後の `is` は `36 is negative` の `is` だが、その後ろの整数は 1 つ(−75)なので `unanimous_integer` が通る。
  **この 2 例では結果として「モデルが主張した値」を拾えていた**(other_error になるのが正しい)。
  **2 例を見ただけであり、一般にそうだとは言えない**

**退屈な仮説の点検**(`CLAUDE.md` §7): C が雑音を拾っているなら、回収された行の correct 率は周りより低く出るはずである。
実際は **C で拾えた 601 件のうち correct が 509(84.7%)**、B は 553 件中 486(87.9%)で、**順5 腕1 の全体の correct 率(約 .88。`STATE.md`)と同じ水準**である。
**これは「雑音ではない」と整合するだけで、証明ではない。**

## 4. 変更仕様(**規則 C に確定。ADR-088 決定1**)

- 触るのは **`code/eval/parsers/numeric.py` の `parse` と、`base.py` に置く 1 つの補助関数**だけ
- **現行の経路(正規化 → 最後の印 → `unanimous_integer`)は 1 行も変えない。**値が返ったらそこで終わる
- 返らなかったときだけ、**最終の非空行**の**最後の `is` の後ろ**に `unanimous_integer` を掛ける(**規則 C**。名詞表は持たない)。**掛けるのは `numeric` パーサだけ**(語形・Yes/No・CoT は触らない)
- **`7.5` は今までどおり失敗**(規則3。丸めない)/ **後ろの整数が値違いで複数なら失敗**(規則2 をそのまま使う)

## 9. リスク・不確かさ

- **§3 の数は実装前の見積りである。**公式の遷移表は §6 の CLI が出す。食い違ったら C3 が人間に上げる
- **C(最終行の最後の `is`)は `36 is negative` のような `is` でも錨を打つ。**§3.4 で見た 2 例では
  結果として正しい値を拾えていたが、**2 例を見ただけである**。C を採るなら、この性質を ADR に書く
- **「最終の非空行」に限る**ので、答えを書いてから数字を並べ直す応答は今までどおり `parse_fail` である(§3.3 の最終行)。
  **回収の上限は原理的に 924 の一部にとどまる**(C で 601、残り 323)
- **順6b(PLAN-026)はこの変更の影響を受ける** —— 順6b の run を新パーサで採点するか、
  旧パーサで採って後から再採点するかは、**順6b を回す時点でどちらのコードが入っているかで決まる**。
  **→ ★2026-09-22(その68)決着(§8 H6・ADR-088 決定6)。順6b を先に回し、この実装は順6b の後に main へ入れる。**
  その68 に §5 を読み直した結果、**パーサが触るのは合格条件 (iii)(C1 = ① 前置き のときだけ掛かる)だけ**で、
  **(i) #2・(ii) #3・(iv) 掃引の遠いオフセットはすべて二値群の強制選択なのでパーサを通らない**(ADR-047)。
  新パーサは (iii) を**緩む方向にだけ**動かし、**C1 は §5 の表の最後なので C0・C3・C2 が全部落ちたときにだけ効く**。
  **順6b の後に §6 の CLI で順6b の run も読み直し、旧・新を並べて報告する**(解釈は人間)
- 本実行の run の `predictions/` は git に無い(PLAN-017 F79)。**手元にある 6 run でしか検査できない**
