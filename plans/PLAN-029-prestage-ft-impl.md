## 3. アーキテクチャの詳細設計(実装前に詰める。人間のレビュー対象)

### 3.1 新ベース識別子(I5)のスキーマ(叩き台。未確定)

ADR-093 P2 の決定「revision + 前段run_id + マージ後の重みのハッシュ」を、既存の
`adapter_provenance`(`code/eval/run.py`)や `outcome.json` の記録形式に類推して設計する必要がある。

- **候補フィールド**: `base_revision`(マージ元のHF revision)/ `prestage_run_id`(前段FTのrun_id。
  `runs/<id>/` を指す)/ `merged_weights_sha256`(マージ後の重みディレクトリのハッシュ)。
- **保存先**: 新ベースの重み自体をどこに置くか(`runs/<prestage_run_id>/merged_base/` か、
  別の `models/` ディレクトリか)は未確定。容量と `.gitignore` の扱い(既存の `runs/` と同じ運用にするか)
  も詰める必要がある。
- **既存コードとの接続点**: `code/eval/model.py:359` の `attach_adapter` は現状アダプタパス1本を
  受け取る。新ベースを「素のベースの代わり」として `model.name`/`model.revision` の位置に置くのか、
  専用のフィールド(`model.prestage_base`)を新設するのかは未確定。

### 3.2 前段プールの非交差検査(I3)

既存の `pool_disjoint` 検査(`code/data_gen/pool.py`。PLAN-001 §4.6 規則3)は評価プールどうしの
非交差を確認する仕組みである。前段の**訓練**プールと主実験の**訓練域+評価域**の非交差を検査する
経路は新規実装になる可能性が高い。既存の検査を拡張できるか、別関数にするかは実装時に決める。

### 3.3 順6b相当の再実行(I7)の運用

P6(前段FT後に順6b相当を新ベースごとに再度行う)は、新ベースが2つ(③-ii・③-iii)あるため、
順6b の7本の config・実行手順をそれぞれの新ベース向けに複製することになる。**config の複製を
手作業で行うか、テンプレート化するか**は実装時に決める(PLAN-026 の config 群を参考にできる)。

## 5. GPU 見積り(叩き台。PLAN-028 §7 より詳細化は未実施)

- **前段FT本体**(③-ii・③-iii それぞれ1本): 規模はP7(主実験のFTと同程度から開始)より
  主実験1条件分のFTと同オーダーと見積もる。**具体的なGPU時間は主実験のLoRA訓練の実測値待ち**
  (`STATE.md` の現在のブロッカー。LoRAグリッドが未決のため主実験自体もまだ実測が無い)。
- **各新ベースでの `ident` を含む全条件の再訓練・再評価**: 既存の主実験相当(40 run 見積り)が
  **新ベースの数(2)だけ**かかる可能性。単一変種の場合のおよそ2倍(PLAN-028 §7 と同じ見積り)。
- **本 PLAN のレビュー後、I1〜I8 の実装が進んでから実数の見積り表を作る**(PLAN-026 §10 と
  同じ形式を想定)。**10 GPU時間を超える実行は人間の承認が要る**(`CLAUDE.md` §2)。
